# Design：如何修复并保留数据契约

> 当前增补：mpc3 实测已证实ACK/Hit同号回归。下列§10是上一轮实施历史，不是最终正确性证明；最新设计补充见§11。

## 1. Context 与不变量

本设计依据 [审计报告](../../../docs/tasks/mp-client-and-sushi-audit-20261002.md)。根因摘要：服务器记录行发布正常，不代表客户端槽位指向该记录；创造库存 AddSlotItems 不发网络钩子，而拖拽包会发全库存，因此下一次拖动“偶然修复”上一次改号。Glock 7→12 的日志、旧记录 5/1185 和新记录 20/1200 支持此链，未取得视频时刻客户端 slot value。

不变量：服务器唯一分配编号和结算玩法；模板 0/1023 与历史 ID 不变；普通移动保留完整 value/记录；复制才分离；槽位数值和记录必须属于同一世界/会话；丢失数据不猜默认值；错误恢复不吞数量或覆盖后续操作；持久记录不因显示修复重置。

耐久数值设计不在本轮调整。使用记录表是正确方向；每发更新现有行而非重新分配。原版耐久接口的 -1 是防止有限物品位段被原版磨损覆盖，但它也让第三方误分类，需要明确的实例能力契约。

## 2. Goals / Non-Goals

目标：四个实际客户端症状从状态根因消除；新增枪立即可用；快速选择、网络迟到、世界切换不污染状态；玲兰相关库存移动不破坏身份或数量；哪些组合支持、哪些缺桥、哪些未测可明确区分。

本轮不重做存档格式、不回收 ID、不统一改所有第三方、不给不存在的未来联机包编造兼容、不重写已经通过本轮用户握手的传输层。新工具/日志仅覆盖必要证据；不为一次音效/外观验证建大型自动化。

## 3. 首轮先验证关键链

在现有 mpb 实际核心和实际平台 DLL 建立最小失败基线：

1. 创建两个独立内存端点/镜像和真实创造库存，确保 OpenSlotsCount 已设置。
2. 服务器从 AK 模板第一次开火 → 新 ID、弹量 29、槽 value 改变；截获实际网络输出，查看有没有对应槽更新。
3. 客户端只得到记录、槽仍模板时，确认 HUD 仍 30；再应用真实库存同步包后是否立刻绑定新记录。
4. 皮肤模板 1 实例化，随后拖入模板 2；捕获库存包快照是在实例化前还是后，验证“上一把变正常”的时序。
5. 用两个物理副本/伙伴库存让 Glock 7→12，双方分别检查槽位、ID、revision、弹药、耐久，而不是只检查一行序列化。

这些检查先复用诊断 Probe 的输入身份，不照抄它的预期错误作为通过标准。对新实现断言应反转为正确结果。若证伪假设，在此更新原因，再改实现；不强迫代码配合规划。

## 4. 事务提交与网络发布

### 4.1 文件入口

| 入口 | 当前职责 | 建议修改职责 |
|---|---|---|
| `World/ScGunMutation.cs` | 事务、分配/分离 ID、库存替换、回滚 | 在最后成功点产生一次提交结果通知，不在未完成事务中发布 |
| `World/ScGunRecovery.cs` | 创造槽替换、退款/补偿 | 成功回滚/补偿也报告最终槽状态；不复用失败提交的通知 |
| `World/ScInventoryTransaction.cs` | 私有 epoch | 保留本地版本用途；不要把它误当平台库存通知或网络版本 |
| `Net/ScNetMirror.cs` | 按 revision 发记录 | 与槽映射刷新协调；记录发失败不标已同步；晚加入完整状态 |
| `src/ScCsgoNet/*` | 真实 MP 包表/发送入口 | 隔离平台库存更新能力、校验接收来源/拥有者/会话 |
| `World/SubsystemScGunBlockBehavior.cs` | 模板实例化、复制扫描、枪输入 | 使用统一提交路径；不要额外绕过同步接口修某个槽 |

### 4.2 先选择最小可行发布方案

**首选评估现有平台库存同步能力**：适配器引用 Multiplayer，可调用其已验证的 `InventoryPacketHelpers.MarkInventoryDirty/QueueInventorySync`（核对实际目标 DLL，不只源码）。核心通过可选接口或提交事件告知适配器。单机实现 no-op；每帧每个真实库存合并一次，不每发都全量扫/发。

先用此方案验证：

- 库存包是否只更新指定实体的正确组件；玩家/创造库存和第三方真正存储是否可识别。
- 队列是否复制槽位快照；记录先发/槽先发、同帧连续两次提交、跨线程投递是否会错序。
- 被改号的持有者以及所有观察者是否收到。仅通知开火客户端不够。
- 平台旧库存包是否能晚到覆盖新值；当前平台存在单调版本或顺序保证吗？必须通过实际队列/传输实现建立结论。

**如果现有库存包不能满足行为规范**，新增窄的 CS 状态消息，携带一次权威提交的槽身份和记录。不要同时维护两条相互覆盖的库存权威写入路径。记录为何现有路径不足，再决定新增。

建议的逻辑字段（不是立即固定线格式）：session/world token、authority revision、inventory identity + generation、slot、expected old value、new value/count、record ID/revision/state、operation ID；若已有平台字段可提供同等保证，复用。

客户端应用原则：

```text
校验服务器来源与会话
→ 验证库存仍是该实体/组件/频道代次，槽合法
→ 验证消息不旧于已应用版本
→ 确认依赖的记录可读；不齐时标 pending 并有界补取
→ 应用槽位和记录为同一次可观察更新
→ 撤销旧选择的预测/动作引用，绑定新实例
→ 返回确认或依赖已有可验证的可靠顺序机制
```

规范要求“观察上的一致性”，不是要求引擎有跨进程数据库事务。槽先到或记录先到可以暂存；不能把后来的玩家拖动覆盖回旧槽，更不能让 pending 期间无限射击。

### 4.3 去重、失败、恢复

- 只有 Commit 完成验证、库存替换、记录发布及最后检查后才入发布队列；AfterRecordWrite 抛出造成回滚时不可提前发成功。
- mutation 成功、发送失败：服务器状态有效，不反向撤销玩家事务；保留待同步项，按有界策略补发/请求完整状态，pending/retry 不重复分配 ID。
- 重复消息：同 operation/revision 应幂等；不能重放扣弹、消耗材料或复制分离。
- 乱序旧消息：丢弃或要求重取，不盖新值。承诺前检查平台库存消息与新消息混用的顺序。
- 回滚：只恢复本操作有确证拥有的差额，避免覆盖此后别人已经移动的枪；无法确认的保留已有补偿机制和证据。
- 静止的新皮肤枪也必须收敛，不靠再次开枪/拿另一把/定时存档触发。
- 正常开火 ID 不变，只有记录行更新；普通移动不增加 Next。受影响库存/记录合并发布，记录频率沿用现有合理值，先量化数据包/扫描成本后调整。

## 5. 客户端预测和输入

### 5.1 权威状态与展示状态分开

当前 `PredictShot` 直接改 MirrorRecord.Rounds，再按差值估计服务器确认，`ClientTick` 写回旧 ServerRounds。这会让 HUD、换弹判断和其他读取者混用预测与权威。

建议：保留最近服务器 snapshot 不变；预测表保存本地待确认操作/扣弹数；HUD 取“权威弹量减去合法未确认预测”。选择实体/世界/枪改变即撤销旧预测；确认应关联操作序号/服务器确认水位，避免把服务器别的原因减少弹量当作本地射击确认。

无需同时新增两套存档状态；预测全部运行时。若采用更小改动，必须仍证明镜像读者不会被过期预测污染，不能仅把 timeout 调长。

建议键：`session + controlled player + selection generation + record identity`。重连、退出世界、角色替换、死亡、模板变实例、复制 7→12 都是生命周期检查点；旧 ID 留在其他槽里不代表旧预测仍合法。

模板首次开火有两种可行策略：先服务器实例化再接受射击，或客户端保持临时预测直到收到权威新 ID 并按确认映射。优先实现前者的最小合理延迟/反馈；不要在客户端猜全局 ID。任一策略必须达到第一次使用能正常扣弹和继续射击，不能永久锁新枪。

### 5.2 操作指向正确的枪

在 `ScNetGuns.SendInput/ReceiveInput` 定义选择身份：槽位、完整 value/record ID、选择递增序号（或等价）。服务器从连接解析操作者，验证其当前库存/选择，身份不匹配时停止旧操作并发权威更正。切换/拖动与开火跨包时需要明确应用顺序。

不能仅比较 ID：模板是共享的、新实例化可能已在服务器改号；必须允许“该客户端旧模板选择对应服务器这次合法实例化”的一次确认映射，而不是把所有首次开枪永远拒绝。

计数事件与持续状态分开：开火短按、换弹、次要操作按序号去重；按住射击带租期，服务器在更新超过有界时限后清 Dig/Custom/可执行队列。实际阈值依据 0.25s 正常刷新、目标延迟/抖动和测试选定，写出取值依据；本规划不把臆测的毫秒数设为产品要求。

超时不能取消已提交的一发，也不补发断流期间无限积压操作；恢复后需要新鲜输入。手雷/C4 的持续按键路径检查同类问题，若共用租期则保留它们各自取消语义。

### 5.3 数据兼容

布局/schema 保留。网络字段改动应在适配器握手中协商；不复用旧 opcode 的旧长度格式却保持同协议号。记录新协议与 Full/Lite/Agents 的核心兼容身份；不要把正常不同资源 edition 判成不兼容。

## 6. C4 声音的最小修复

位置：`SubsystemScC4.Sound`、事件循环，及 `ScNetGrenades.Sound` 广播。
目标角色表：

| 场景 | 下包者本机 | 房主旁听 | 其他客户端 |
|---|---|---|---|
| 房主下包 | 房主播放一次 | 同左，无第二份 | 服务器事件播放一次 |
| 客户端 A 下包 | A 本地预测一次 | 房主本地世界声一次 | B 收广播一次 |
| 专用服务器（若支持） | 无音频输出依赖 | 不因没有声音设备中断 | 正常发送 |

修本地播放条件以区分“本机是拥有者客户端”和“本机是权威房主”，保留排除 A 的远端广播。检查 initiate、各 keypress、plant 完成、取消再开始；只修按键样本的一处会漏同链其他声音。不要删除 shownBy 排除导致 A 双播。

声音失败只损失该声音，不应回滚 C4 或中断世界更新。本轮轻量包不以全量立体声 Ogg 解码问题解释，另保留已有资源问题记录。

## 7. 玲兰适配：逐类能力而非一个支持开关

### 7.1 当前包与既有保护

实际包是 SushiBase DLL `55d1a7c3…`、SushiTool DLL `78c6984f…`，来自指定单机 Mods。文件名 v3.0.3/v3.0.4，内部版本均 3.0，适配键应包括程序集/接口身份，不只看显示版本。

保留 `ScInventoryIdentity`、`ScSushiInventory`、`ScGunHolders` 的现有真实库存映射、频道库存扫描、稀疏键处理、已完成补偿保护和不猜目的地原则。正式 `SushiInventoryRegression/SushiSyncInventoryRegression` 已有复杂夹具，先读再增补，不能用假 Sushi 类代替实际接口。

### 7.2 不可堆叠实例

危险条件是 `ScNoDurabilityBlock.Durability=-1` + IsPlaceable=false + MaxStacking=1，被 Sushi “无耐久非放置物堆叠”命中。

先检查能否用 CS `GetMaxStacking(value)`/已有注册接口保证返回 1，以及第三方在自己扩大容量时是否仍服从；实际 SushiUtils 会在 getter 之后再扩一次，**仅覆盖 GetMaxStacking 不足以声称已修**。不把 Durability 改为正数破坏位段保护，不偷偷关用户全局堆叠开关。

选择优先级：官方排除/能力接口 → 我们拥有的库存适配边界 → 为维护者准备窄的 CS 独立实例排除建议。若现有第三方完全绕过所有我们可控容量检查，明确这一能力仍依赖第三方，而非静默宣布兼容。

既有 count>1 的同 ID 实例：不得截断为 1 或清空。设计服务器隔离/逐份拆分方案时先检查空槽、容量、记录容量和可回滚性；没空间则保留原值/数量并清楚提示，直到可安全拆分。拆分是否应剥离成长遵守已有真实复制规则，不能连带清原件成长。模板是否允许堆叠单独决定，不能用“模板无状态”推出“实例也可堆”。

### 7.3 真实存储与操作者

建议适配层回答四个问题，而不是继续按类型名到处加判断：

1. 某个视图/代理对应哪一个真实库存和槽位？映射是否一一对应、是否会换频道？
2. 此操作由哪个连接/玩家发起，允许访问哪个库存？
3. 修改后怎样通知库存网络层，怎样查询权威版本/恢复快照？
4. 保存/重载后如何识别同一存储，频道被删除再建如何区分代次？

保持核心不引用 Sushi 类型，用已有可选反射集成核对接口；必要信息不存在时报告能力缺口，而不是假设 item 相同就是别名。

个人箱指向全局 `ComponentPlayers[0]`，我们去重只会忠实映射这个错误绑定；需要在目标联机桥明确请求者。不能用“客户端本地第一个玩家”代替服务器连接拥有者，也不能让客户端借箱子请求改房主背包。当前无第三方修改授权，输出该接口的最小建议。

同步箱真正存储在 subsystem 字典，普通实体 inventory ID 不够；复用平台已有 Sushi 通道桥时查明 Android 是否提供它、频道代次、消息过期和快照应用规则。CS 自有包正常不改变它的外部能力。

### 7.4 批量移动与自动功能

普通单线程 Add→Remove 的中间态不一定被扫描，不臆造每次复制；但应防同操作的回调/分帧/网络快照误判。转移应在服务器完成，并在提交后发布源/目标/掉落物与受影响记录。扫描是最终一致性兜底，真实复制的确认不依赖单次瞬间状态。

整理、平均分配、一键存取：保留完整 value；不同 ID 的同名枪各保状态；同 ID 数量副本按安全拆分处理。外部直接 m_slots 写入可能不走我们 Changed，需比较真实值/数量/存储代次，或接收提供方的提交通知；不要把私有 epoch 当所有第三方写入日志。

自动补位：动作开始绑定选择身份；自动切到另一把枪时取消旧 reload/burst/C4，不能继承旧动作的扣弹/材料提交。

死亡保物：实体消失/重生时保留物品实际引用与记录，服务器完成恢复，旧实体待处理操作失效；不同端不各自补发一份物品。提供方只存 value+count 时，不能未经设计新增自动世界备份。

机器/吸物箱：服务器同时结算掉落物 Count/ToRemove 和目标库存，客户端只显示；短暂停机/重连后重取状态。不存在目标联机桥则该功能兼容项待处理，不影响已完成枪核心修复。

### 7.5 频道持久化缺陷

真实 DLL 最小复现：0/1/2 → RemoveChannel(1) → Save 使用字典 [1] 抛异常；当前 UI 可达性未知。给维护者建议：保存真实键列表、按键加载、保留频道引用、允许旧连续格式迁移；不要重排频道号使箱子指错库存。另讨论 UUID/代次是否由提供方长期支持；不是本轮擅改 CS gun schema 的理由。

我们既有补偿在重载后无法确认原频道对象时留债是安全优先的限制，应保留并给出可读状态；不能仅凭相同数字向新频道退款。

## 8. 有关其他发现的处理

枪命中姿态 body-only fallback、地形 6 次修补仍不一致：各建一行独立调查状态，引用原日志坐标/时间。先确认是否与实际 candidate/source 身份一致及是否命中现有兼容 fallback；没有根因时不把它们并入库存大改，也不从报告消失。

## 9. Alternatives / Risks / Rollback

- 拒绝“客户端猜 ID/补满弹”：会覆盖服务器状态，制造复制和弹药问题。
- 拒绝“把刷新绑到开背包/拿下一把”：正是当前偶然恢复方式，静止最后一把仍错。
- 拒绝“只在槽 0 特判”：证据指向模板/改号，其他槽和复制也受影响。
- 拒绝“所有第三方库存均按独立对象扫描”：个人箱/频道代理会重复分配，现有保护已证实有效。
- 拒绝“把全部枪字段挤回 item value/改 UUID 存档”：非必要破坏兼容；本轮协议运行时字段不等于持久格式改版。
- 风险：全库存广播过多、交叉消息覆盖、握手旧版不兼容、共享库存被未授权操作者引用、补偿误发、客户端视觉动作与权威确认不匹配。verification 对这些逐项覆盖。
- 回退：候选未安装时保持既有 output 证据与正常发布规则；协议不兼容应明确拒绝。已落盘的正常游戏记录保持可读，不通过清枪表恢复。不删原件、历史备份或为回退自动改原世界。

## 10. 实施决定记录（2026-10-02，VPS 执行）

本节记录执行时的实际选择及依据；与前文建议不同处以本节为准，前文保留为规划时的考虑。结果登记在 verification.md，不在这里。

### 10.1 槽位发布：复用平台库存包，不新增第二条库存写入路径（§4.2 的首选方案成立）

核实对象是用户实际 Windows 1.9.3.2 平台的 `Survivalcraft.dll` / `Survivalcraft.Multiplayer.dll` 反编译与真实程序集运行（`tools/NetLoopCheck`）：

- 根因确认：`ComponentInventoryBase` 的增/删/置槽都走 `OnSlotChange` → `OnNetworkInventorySlotChanged` → `InventoryPacketHelpers.MarkInventoryDirty`，帧末 `FlushPendingSync` 发 `InventorySyncPacket`；`ComponentCreativeInventory.AddSlotItems` 只写 `m_slots`，`OnSlotChange` 为空，不发任何通知。拖动包 `DragDropItemPacket` 处理后会广播整份库存，这就是“下一次拖动把上一把修好”。
- 平台库存包寻址：实体 ID + 组件类型全名，客户端用 `SetSlotValue` 逐槽应用，目标精确；所有观察者都收到（广播）。非实体组件的存储（玲兰同步箱的 `SushiSyncInventory`）不能这样寻址，CS 不替它发，登记为提供方桥的职责（只告警一次，不猜）。
- 顺序：平台所有包（含 CS 自有包 197）都在通道 0 以 ReliableOrdered 发送（`NetworkServer.Send` / `RelayHost.Send` / `NetworkClient.Send` / `RelayClient.Send`），入队即序列化。因此同一连接上“先入队先到达”，旧快照不会晚于新快照到达；库存包本身没有版本号，其防旧依赖这一条通道顺序。新会话是新连接加完整工程快照。
- 结论：现有平台包满足“精确寻址、所有观察者、按序到达”，不新增 CS 库存消息，避免两条库存权威路径互相覆盖。代价是整份库存（每槽 12 字节，创造库存含全部目录槽：离线夹具 4010 槽为 27.8 KB），与平台自己每次拖动后的广播同量级；只在槽值真的被服务器改写时发（新枪首次事务、复制分离、模板实例化、回滚/补偿、直接写槽），普通每发只发记录行（约 160 字节）。

发布点与顺序（`Net/ScNetSlots.cs`）：

1. 所有记账的槽写入（`ScGunInventoryJournal` 的 Remove/Add/ReplaceCreative、`ScInventoryTransaction.ReplaceWithCost` 的创造分支、护盾直接写槽、延迟补偿实际生效时）先标记“已触碰”。
2. 事务结束点（`ScInventoryTransaction.Changed`，成功与回滚都会到达）把该库存登记为“本帧待发布”。发布失败不回滚事务。
3. 适配器在每帧所有子系统更新之后（平台 `SubsystemUpdate` 钩子，早于平台自己的帧末库存刷新）调用 `ScNetSlots.EndOfFrame`，依次入队：变更的枪记录行 → 每个待发布库存一份平台库存包 → 射击确认。客户端因此先读到记录，再读到指向它的槽，最后是确认。
4. 快照取自帧末：回滚的事务发布的是恢复后的槽，同帧多次事务只发一次。`AfterRecordWrite` 失败路径不会发出被放弃编号的记录行（记录行只在帧末或 0.1 s tick 发）。

相反顺序与丢失的处理：槽先到而记录未到时，客户端该枪处于既有的“等待服务器同步”（`ScGunBlock.AwaitsRecord`，不可用、不预测、不发扳机）；持续 0.5 s 后向服务器索取该记录（`OpWant`），间隔翻倍，最多 5 次（共约 15 s），之后只等待不再发。记录行按 revision 只升不降应用，晚到的旧行丢弃。记录行未能入队时不标记已发送，下一 tick 重发，不重跑玩法事务。

### 10.2 预测：不写镜像，按“世界表 + 玩家对象 + 选择序号”保存本地未确认射击

- 镜像（`ScGunRegistry`）只保存服务器发来的值。本地预测是一个时间戳队列：每次显示的射击入队，服务器确认一发出队一发，超过 1.0 s 未确认的出队（服务器没有开这一枪）。HUD、客户端开火/换弹表现读“服务器弹量 − 队列长度”（`ScNetGuns.ShownRounds`，`ScAmmoReadout.ReadPredicted`）；其余读取者读服务器值。
- 确认用服务器计数而不是“弹量差”：服务器对每个远端玩家按其当前选择累计已提交射击数，紧跟记录行在同一有序通道发给该客户端（`OpShotAck`）。这样换弹、别的原因造成的弹量变化不会被误当成确认，也不会把确认当成换弹。
- 选择序号：槽位、库存或物品变了就是新选择，预测与未消费的按键随之作废；新枪从模板变成实例（同槽、同型号、fresh→有编号）算同一选择，与单机 `ScHeldWeaponSelection` 的判断一致。世界表引用、玩家对象引用任何一个变了，旧预测即失效；世界关闭、会话重新接受时显式清理。

### 10.3 输入：带序号与选择身份；服务器只对自己持有的那把枪执行

- `OpInput` 增加：消息序号、选择序号、槽位、物品值。服务器丢弃序号不更新的消息（重复/重放不重复计数）。
- 服务器比较“客户端所指的槽与物品”和自己为该玩家持有的：一致则接受；不一致但服务器刚把该槽从客户端所指的值改写成现值（`ScGunMutation` 提交时登记，5 s 内有效，可连锁）也接受，这就是“模板首次开火后第二发仍带模板值”的合法映射；其余视为过期选择：松开扳机、丢弃未消费的按键，不对服务器当前持有的枪做任何事。过期持续 0.5 s 且涉及 CS 枪时，向该客户端单独重发其库存（最多每 2 s 一次）作为权威更正。
- 活动槽不一致的收敛：手上是哪一格由客户端决定（平台自己的活动槽消息不经校验直接设置服务器副本）。客户端连续 0.5 s 都指向另一格时，说明服务器副本漏了一次变化（例如服务器为该玩家做的投掷后切槽，或丢失的消息），服务器改为采纳客户端所指的槽，并用平台的活动槽消息通知其他客户端（不发给该客户端自己）。物品值仍不一致时继续按上一条处理。
- 选择变化时丢弃上一把的未消费按键与按住状态，再应用新消息里的当前状态。
- 客户端显示中的换弹（客户端只显示，服务器结算）：新枪第一次换弹时服务器在插入弹匣那一刻分配记录，客户端该槽的值随后从模板变成实例。同一选择下这种变化不再打断正在显示的换弹（`ScReloadTransaction.FollowAllocation`）；换成另一把枪仍然取消。
- 租期：按住状态与未消费按键在最后一条消息后 1.0 s 失效。依据：客户端在状态不变时每 0.25 s 刷新一次（开火且准星移动时每帧），1.0 s 允许连续三次刷新晚到或卡在有序通道的重传之后，同时保证客户端沉默后一秒内停火；已提交的射击不撤销，恢复后按当前状态继续，不补打。未覆盖：真实链路抖动分布（需实机），极低帧率客户端（<1 fps）会表现为断续开火。
- C4 下包键与手雷按住沿用同一租期：下包键过期按“松开”取消本次下包；手雷按住过期取消本次投掷（不扔出、不扣物品）。C4 键在按住时改为每 0.25 s 刷新（原 0.5 s）。

### 10.4 协议

CS 网络协议 4 → 5（输入消息格式变化，新增 `OpShotAck` 42、`OpWant` 35）。握手已有“协议不同则拒绝并说明”的路径，mpb（协议 4）与本候选互连会被明确拒绝，CS 武器停用，不会静默错读。存档布局、枪表 schema、物品编码不变。

### 10.5 C4 声音

`SubsystemScC4.Sound` 的本机播放条件改为：无拥有者，或拥有者是本进程玩家，或本进程是房主（`HeardHere`）。先向其他客户端广播（仍排除下包者），再本机播放；本机播放失败只损失该声音。倒计时提示音与客户端自己的放置声也走同一受保护的播放函数。

### 10.6 玲兰堆叠：我们能做到的边界

- `ScGunBlock`（及两种模板）覆盖 `GetMaxStacking(value)` 恒为 1，不再跟随会被玲兰 `ApplyMaxStackingTweaks` 改写的 `MaxStacking` 字段。凡是向方块询问容量的库存（玩家背包、箱子、合成）因此不再把枪叠起来。
- 玲兰自己的容器（箱子、同步频道、机器）用 `SushiUtils.GetNewMaxStacking(block, value)` 自行计算容量，在方块回答 1 之后对“不可放置且无原版耐久”的物品再放大，仍可在一格放入最多 4 把**完全相同值**的枪。CS 无法从方块侧否决：把 `Durability` 字段改成非负可以绕开它的条件，但该字段是原版/第三方对“有耐久工具”的分类依据，影响面无法在本轮核实，未采用。此项登记为提供方可控的能力缺口，并给出最小补丁建议（见提供方说明文档）。
- 既有/新出现的同编号多份堆叠采用“保留并拒绝”策略而非自动拆分：整叠保留原值与数量，使用时以专门结果 `Stacked` 拒绝并提示玩家分到不同格子；分开后的副本在首次使用时按既有“真实复制”规则获得自己的记录（成长不随副本复制），原件编号、弹药、成长不变；编号用尽时拒绝并原样保留。未实现自动拆分，原因是它需要新的跨槽搬移事务与补偿，风险高于收益（不同记录的枪值不同，本来就不会被叠在一起；同值堆叠只来自复制或新枪模板）。

## 11. mpc3 用户实测后的设计修正（2026-10-02）

详细入口：[新增诊断与处理顺序](../../../docs/tasks/mpc3-feedback-subworld-20261002.md)。本节未实施。

### 11.1 消息路由先于预测算法修补

§10.4的ACK42与既有Hit42冲突。实际注册用同方向字典，后者覆盖前者。改唯一opcode只是第一步：建立全生产模块注册测试（包括Feedback和可选Tactical），在注册层防止不同语义handler静默覆盖，并处理重复初始化的正确清理/幂等。

ReceiveHit校验outcome属于1/2/3、字符串/距离合法、payload完全消费；ACK也验证选中序号/计数/长度。错误消息不能画白杠或假击杀。混版协议明确拒绝，不能认为仍叫1.4.0就支持新旧ACK语义互换。

### 11.2 确认与换弹闭环

现有服务器累计Fired+客户端Queue时间戳不是逐发配对。修冲突后验证：旧预测超时出队，再收到旧ACK时不可扣掉新预测；记录revision和ACK水位跨帧到达时不可把同一发扣两次。优先将确认与对应权威快照关联，再决定是否同消息提交；不以加长timeout替代身份。

自动换弹不能仅由本地ShownRounds==0启动动画而无明确权威结果。客户端请求携带选择/动作序号，服务器接受后按真实状态机提交，完成/取消关联同一动作；实际弹量2而预测0的路径必须在完整UpdateGun链中运行。手动按R、空弹按住自动换弹、松手、切枪、服务端拒绝分开覆盖。

### 11.3 中立与邻近同目标

用户要求是行为结果，不是限定实现方式。先核验既有群体响应；若旧效果来自所有匪各自主动索敌，关闭主动索敌后必须补显式局部响应。用服务端一次受击事件的victim位置/attacker身份枚举附近匪，跨Squad/Source，避免Alert再次广播造成链式全图扩散。

建议默认32格作为候选（用户未指定数值），保留既有有限遗忘/距离脱战与烟雾/墙体射击检查；形成敌意不等于视线透视。致死一击先取位置和攻击者再处理实体移除。环境伤害和假hit提示不算玩家挑衅。伙伴不能仅凭Enemy类型开火；明确保护主人、自己受击、协助主人已开始战斗的合法例外。自然、召唤以及旧存档Source缺省都覆盖。

### 11.4 子世界迁移接入

分表正常，不能直接共享或合并整张registry。当前ScGunTravel v3可处理任意目标但依赖玩家XML中的快照以及ProjectXmlLoad时机。用户现提供0.41.16实包：实际TravelerSnapshot仅捕获物品整数等字段，目标OnPlayerAvailable直接恢复，确定未携带CS记录且绕过该导入时机。实际DLL复现了同号同型源7发读成目标23发。完整方案与源代码位置见 [通用物品迁移分析](../../../docs/tasks/universal-item-travel-analysis-20261002.md)。该版本不等同日志0.41.15，实机旅行未测。

先在源世界验证携带槽与记录、稳定世界/枪身份，目标用稳定身份映射本地ID并一次提交槽与记录；同号同型也不能直接复用。统一可选版本化迁移API、provider payload与提交receipt，使完整XML和自定义晚恢复共用一个记录算法；提供方仅接生命周期。不能在只剩无来源整数时靠扫描猜原记录。晚恢复增加对应最小适配，重复导入幂等，失败不覆盖另一持有者。已有错误物品只能用来源记录证明恢复，不能猜满弹/皮肤；不擅写用户原世界。

## 12. 实施决定记录（2026-10-02，VPS 执行 §11；mpd1 实施，交付为候选 mpd2）

本节记录 §11 落到代码时的实际选择及依据。§10 的协议 5 设计中“单独的射击确认消息”“按时间超时结算预测”两点被本节取代，其余保留。

### 12.1 消息编号：一个编号一个含义，注册层拒绝第二个处理器

- `ScNet.OnServer/OnClient` 经 `Claim`：某编号已属于另一个方法时，后来者被**拒绝**并记入 `ScNet.Conflicts`、写错误日志，先注册者保留；两个方向共用一张编号表（同一编号不能既是客户端消息又是服务器消息）。同一方法再次注册视为同一注册（重复初始化幂等）；`ScNet.RegisterCore()` 是模组加载器与离线检查共用的唯一核心注册入口，自身带一次性标记，不会重复订阅事件。
- 分发器统计 `ScNet.Dropped`（处理器抛出→整条丢弃）与 `ScNet.Unread`（处理器未读完）。`ScNetReader.Finish()` 要求消息恰好读完；Hit/Damage/HitSound/Voice/Notice/Reload/Records/Input 均调用。
- `ReceiveHit` 先读完并校验（outcome 只能 1/2/3，距离 0–4096，无多余字节）再计数与显示；`ScCombatFeedback.Record` 对其他数值不画任何标记。mpc3 把 selection/count 解析成 outcome 的路径由此在两层都被拒绝。
- 离线检查（`tools/NetLoopCheck`）改为调用同一个 `RegisterCore`，再按各可选包自己的加载器调用注册（探员包 `TacticalNet.Register`、外观集成 `ScNetAppearance.Register`）；对没有 `RegisterCore` 的已交付构建，按其加载器顺序逐模块注册并比对处理器表，所以同一组断言能在 mpc3 上复现覆盖。

### 12.2 射击确认：随记录消息到达，按编号结算，不按时间

- 取消独立的确认消息。`OpRecords`（32）每个客户端一条，末尾带该客户端自己的确认（selection、服务器所持物品值、Fired、Skipped）；没有记录变化而确认有变化时发一条 0 行的记录消息。客户端在同一条消息里先应用记录行再应用确认，因此不会读到“扣了弹但还算作未确认”（多扣）或“确认了但弹还没扣”（回跳）的中间态。
- 编号规则：客户端对当前选择下自己**显示过**的射击计数（Shots），随输入上报；服务器记 Fired（已提交）与 Skipped（该客户端显示过、但服务器不会再打的：扳机已松、正在换弹、空仓、枪不可用）。第 n 发在 Fired+Skipped ≥ n 时结算。待确认数 = Shots − 已结算，显示弹量 = 服务器记录 − 待确认数。迟到或重复的确认只能推进同一选择的水位，不能抵扣更新的射击；另一选择（收枪再取出、换枪、换世界）的确认整条忽略。服务器多打出客户端未显示的一发时，客户端的计数跟上服务器，下一发是新编号。
- 新枪第一发：确认里的物品值是服务器分配后的实例值，客户端槽位此刻还是模板，确认暂存；槽位变成该实例时（同帧稍后的库存包）由 `ScNetGuns.Observe`（每帧枪械更新一开始调用）立即应用。
- 没有按时间的结算。只有服务器 5 秒（`PredictionGiveUp`）没有任何答复时才本地放弃并写一次警告、计入 `GiveUps`：这是故障路径，离线用例要求正常场景下该计数不变。不采用“延长超时”。
- 记录行仍按 0.1 s 节流发送（有库存发布的帧立即发）。

### 12.3 换弹：客户端显示，服务器执行并答复

- 客户端每次开始显示换弹（按键、触屏按钮、显示弹量为 0 时扣扳机）都生成一个请求号，随下一条输入发出（`Reload` 标志＋id）；服务器对每个请求给出答复 `OpReload`（37）：Accepted、Refused、Completed、Cancelled，并带服务器当时的弹量。服务器自己开始的换弹（它那边先打空）以 id 0 的 Accepted 通知，客户端据此显示。
- 服务器收到请求时若该客户端还有“已显示、服务器未打”的射击，且服务器这边扳机仍按着、枪里还有弹，则先按自己的节奏把这些打完再开始换弹（客户端已经播放了它们的弹道与声音）；扳机已松或枪不能开火时立即换弹，未打的记为 Skipped。请求在服务器因枪忙而不能开始时最多保留 1 s（`ReloadRequestLease`），过期答复 Refused。
- 客户端：Refused/Cancelled 且 id 相符时撤回正在显示的换弹；显示的换弹动画播完**不代表**装弹成功，弹量始终读服务器记录；在服务器对上一次换弹给出结果之前（或动画时长＋3 s 的保护期过后）不再发起新的换弹请求，避免延迟较大时“动画播完、满弹未到、又播一遍”。
- （历史，已被 §13 取代：下面这条“保留的表现”正是 mpd2 实机的一发回升，§13 起不再保留。）已知且保留的表现：房主帧率低于武器射速所需时，房主的实际射速低于客户端显示的射速；扳机松开时客户端多显示的那几发被记为 Skipped，读数回到服务器值（如实显示，不补弹）。持续按住打空时服务器会把欠的几发打完再换弹，读数保持 0 直到满弹到达。射击节奏的调度（`NextShot = now + interval`）是既有单机行为，本轮未改。

### 12.5 匪徒：默认中立，受击后 32 格内共同报复（候选值）

- 核对结论：此前“附近的都会一起打”来自每个成员各自的主动索敌（32 m、狙击 36 m 的视锥/近身感知），并不存在群体通知；受击只 `Alert` 被打的那一个。用户要的结果是“都中立＋一个被打附近都打同一个人”，因此移除主动索敌后必须补显式的群体响应。
- 实现：`ComponentTacticalEnemy.Update` 不再主动找目标（自然、召唤、旧存档来源缺省一律如此）；靠近、听到枪声（仍只触发有限搜索，不给目标）、召唤暖机及其后的搜索结束都不产生敌意。`TacticalModLoader.ProcessAttackment`（服务器/单机权威）在有效攻击（有攻击者、攻击力>0、攻击者不是匪）命中任一匪时：被打者 `Alert`，并由 `SubsystemTacticalEnemies.Provoked` 以**被打者位置**为圆心，通知 `ProvokeRange = 32` 内所有存活的匪 `Provoke(同一攻击者)`；被通知者不再向外通知（不递归扩散）；不分小队与来源。已在报复一个存活攻击者的成员不被新的攻击者拉走；已对准同一攻击者的不重置瞄准。
- 32 的依据：用户未给数值；取原主动注意距离（32 m）作为候选，等于“以前会自己注意到你的那个范围”。召唤小队最远成员距召唤者 30 格，在该范围内。此值需用户实测确认，记为候选。
- 保留：视线/墙体、烟雾、友军身体遮挡下不开火；报复距离（40 m，狙击 64 m）与看不见攻击者 8 s 后放弃。因此被通知但离攻击者超过自身报复距离的成员会立即放弃——“加入”不突破原有脱战上限。
- 伙伴：`ComponentTacticalCompanion.Hostile` 不再把所有匪当敌人；只有当某匪的目标是其主人、其本人或同一主人的其他伙伴时才主动应战。主人先动手、主人或伙伴被打，仍通过 `ProcessAttackment` 的既有 `Alert` 路径参战。

### 12.6 通用子世界携枪迁移核心

- 文件：`src/ScCsgoKnives/World/ScItemTravel.cs`（`ScTravelEnvelope`、`ScTravelLedger`、`ScItemTravel`、`ScGunTravelApi`）；`ScGunRegistry` 增加 `Travel`、`TryReadRow`、`ImportNew/ImportOver/ImportUndo`；`ScGunTravel.Prepare` 改为调用 `ScItemTravel.Resolve` 与 `GrowthAfter`（同一条“身份→本地编号”规则与同一条成长规则判定）。
- 信封（JSON，版本 1，namespace `zh667.ScCsgoKnives/guns`）：transfer id（导出时生成的 GUID）、来源世界身份（既有 `GunTravelWorldIdentity`，不是目录名）、旅行者标识、schema/layout、成长规则、来源世界的枪方块编号、每把枪的稳定身份＋来源本地编号＋型号＋完整记录行（当前 schema 的行格式，充能以剩余秒数表示）、每个携带槽（槽号、原值、数量、身份；新枪模板身份为空）、SHA-256 摘要。只含旅行者携带的枪，不含整张表。
- 稳定身份沿用既有定义：`SHA256(世界身份|本地编号)`，首次导出/保存时生成并记入 `GunTravelIdentities`；外来记录保留其原身份。XML 路径（`ScGunTravel.Capture`）与运行时路径对同一把枪给出同一身份（回归断言）。
- 目标导入：先整体校验（版本/namespace/摘要/schema/布局/成长规则/每行可解析/槽与身份一一对应），再做计划：身份已在本世界有编号→回到该编号（要求该记录未被旅行者自身库存以外的持有者引用、且型号相同，否则拒绝）；否则取下一个空闲编号。**从不因为编号相同或型号相同而复用**。计划完成后一次写入：记录、身份表、成长规则、回执；任一步失败回滚。返回“来源物品值→本世界物品值”的映射，提供方用它恢复库存。
- 幂等：同一 transfer 再次导入返回回执里的同一映射，不写任何东西（不再分配编号，也不把枪在目标世界里之后的变化改回去）；同一 transfer id 配不同内容→拒绝。回执保存在枪子系统的新键 `GunTravelReceipts`（最多 64 条，仅在发生过运行时导入的世界写出）。不认识该键的构建会丢弃它，后果仅是失去“在途旅程的重复保护”：再次导入会按身份落到同一编号（不产生第二条记录）。枪表 schema 7、布局 6、编号规则、既有键均未变。
- `Complete`：提供方恢复库存后调用，核对每把携带枪在库存里以本世界编号恰好出现一次，才标记完成；否则返回原因（如提供方仍按旧值恢复）。
- 来源即本世界（同一 Project 内的传送）：映射为恒等，不分配编号。
- 导出拒绝：记录缺失或型号不符、同记录叠放、同一把枪携带两份、该枪有待结算击杀、该库存有未归还补偿、表异常。不在目标世界重建新枪。
- 不做的事：不合并世界枪表、不扫描猜测无来源物品、不缓存“上一个世界”、不给坏枪补满。提供方不携带信封时，同号同型碰撞无法事后区分（回归里保留了这一未桥接读数作为对照）。
- 多人：核心按信封与旅行者库存隔离，两名旅行者的两份信封互不影响（已测）；Ancient 0.41.16 自身只允许单玩家旅行，未绕过其限制，不宣称其多人旅行已支持。

## 13. 实施决定记录（2026-10-02，mpd2 残余“停火后回升一发”，候选 mpe 系列）

本节取代 §12.3 末条“已知且保留的表现”与其中“射击节奏的调度本轮未改”。范围只有射击调度、输入发送时机与服务器执行远端射击的判定；确认编号、换弹答复、消息格式、存档与物品编码都没有变。

### 13.1 核对到的机制（在 mpd2 上用扩展后的 GunLoop 复现）

- 两端各自按“自己这一帧看到的扳机”独立决定何时打下一发，且每发之后 `NextShot = 本帧时间 + 间隔`。帧不会正好落在到期时刻，所以每发间隔被向上取整到帧：AK（100 ms）在 100 FPS 实际 110 ms、50 FPS 实际 120 ms、60 FPS 100 ms（单机回归实测，见 verification §11.1）。客户端 100 FPS、房主 50 FPS 时客户端 0.6 s 显示 6 发，房主只打出 5 发；松手到达后第 6 发记 Skipped，读数回升一发。不需要任何传输延迟。
- 帧率相同也会出错：松手消息相对服务器帧的相位、输入成批到达（房主卡顿、有序抖动）会让服务器看到的“按住时长”与客户端不同，结果是少打一发（回升）或多打一发（客户端没显示、服务器扣了弹）。R8 击锤落下前后松手、沙鹰按节奏点射、按住扳机开菜单属于同一类。
- 对照实验（只在临时副本上做，未进入产品）：保留下面 13.2 的稳定时间轴、关掉 13.3 的按上报发数执行，扩展 GunLoop 仍 28/95 失败（100/50 下 15 次短连射仍有 3 次回升）。所以只改 `NextShot += cycle` 不够，交付的方案是 13.2＋13.3＋13.4 一起。

### 13.2 稳定的射击时间轴（单机、房主自己、客户端预测共用）

- `Fire` 里下一发的时间从“这一发**到期**的时刻”起算，而不是从执行它的那一帧：`late = now − NextShot`；`late ≤ ShotCarry (0.05 s)` 时 `NextShot = 到期时刻 + 间隔`，否则（停火后再扣、帧率低于 20、卡顿）仍从本帧起算。于是按住扳机时平均间隔等于武器自己的间隔，单发抖动不超过一帧；不补射：每帧最多一发，停顿不积攒“欠的发数”，帧间隔大于 `ShotCarry` 时退回旧算法。
- 三连发的**轮间**周期按同一规则；轮内三发的间隔、R8 蓄击（`PrepareUntil` 与其后的冷却）、R8 右键速射未改。
- 这是共享节奏的变化：单机下按住连射的实际射速从“间隔向上取整到帧”变为武器标称间隔（例如 50 FPS 的 AK 从 500 发/分回到 600 发/分）。这是消除累计帧误差的直接结果，不是另加的平衡调整；由 `ShotCadenceRegression` 逐帧率记录，手感由用户实机确认。

### 13.3 服务器按“客户端已显示的发数”执行远端玩家的射击，并用自己的时间轴校验

- 对远端客户端的玩家，服务器不再用“此刻看到的扳机”产生射击，而是：`owed = ClientShots − Fired − Skipped > 0`（该客户端报告已显示、服务器尚未执行也未拒绝的发数）**且**服务器自己为这把枪维护的时间轴已到期或在 `ScNetGuns.ShotLead (0.125 s)` 之内（`now ≥ NextShot − ShotLead`）时执行一发。每帧最多一发；弹量、耐久、换弹中、切枪保护、枪身份（槽位与物品值，含改号映射，`ScNetGuns.Holds`）、玩家存活与可操作、输入租期都照旧由服务器检查。
- 上报的发数只是“请求执行到第几发”，不是事实：服务器的时间轴每执行一发前进一个间隔（执行早于到期时从到期时刻起算，晚于到期不超过 `ShotLead` 时也从到期时刻起算，更晚才从当前起算），所以 n 发至少用时 `(n−1)×间隔 − ShotLead`，长期射速不可能高于武器射速；客户端一次虚报 5 发，服务器只执行时间轴允许的（AK：0.08 s 内至多 3 发，后两发各比标称时刻提前不超过 `ShotLead`，随后的一发相应推迟），其余在报告过期后记 Skipped，客户端读数按确认回滚（G11）。没有“按累计发数直接补射”：过期的不补，超速的不打。
- 停火：客户端最后一发与“松开”常在同一条或相邻的输入里。该发的报告到达后 `ShotLead` 之内，即使服务器已看到扳机松开/菜单打开，也照常执行（沿报告该发时的瞄准射线 `ShotAim`）；超过 `ShotLead` 仍未能执行的（服务器长时间卡顿、枪在服务器上不可用）才记 Skipped，读数如实回滚。延迟补射的上限因此是报告到达后 0.125 s，GunLoop 记录每发“报告→执行”的等待（正常节奏下 0，成批到达时 ≤ 33 ms）。
- 反方向：服务器不再因为“晚看到松手”多打客户端没显示过的一发（自动武器、沙鹰点射、R8）。
- R8：开始压击锤仍由服务器看到的扳机决定（预备阶段有可见动作，需尽早开始）；击锤落下改为“客户端已报告这一发，且 `now ≥ PrepareUntil − ShotLead`”。客户端在落锤前松手→没有上报→服务器取消预备，不走火。
- 换弹请求与欠发的先后（§12.3）保留，条件改为“扳机仍按着或报告未过期”。
- 已知边界：客户端在**切枪的同一帧**显示的那一发，到达时服务器已看到新选择，按旧枪的计数不执行（不从另一把枪打出），记 Skipped 并回滚这一发；服务器停顿超过 `ShotLead` 时停火前最后一发可能同样被拒绝。这两种是“真正被拒绝的预测”，回滚是正确结果。

### 13.4 输入在帧末发送

客户端的输入消息原先在 `UpdateGun` 开头发出，带的是上一帧结束时的发数：本帧显示的一发要到下一帧的消息才上报，而本帧的“松开”可能先到。现在在 `UpdateGun` 结束时发送（`finally`，所有返回路径都经过），同一条消息带本帧的按下/松开、发数和瞄准，服务器在一个服务器帧里收到“按下、发数、松开”时能把它们对应起来。消息格式不变。

### 13.5 协议号不变

线格式没有任何变化，协议仍为 6。不同构建之间本来就由握手里的玩法构建标识拒绝（mpd2 与本候选不能互连，提示为构建不一致）；因此不需要为“语义变化”再升协议号。

### 13.6 取值依据与未决

- `ShotCarry = 0.05`：覆盖 20 FPS 以上的一帧取整；更低帧率退回旧算法，避免低帧时一帧内“应当”打出多发的补射问题。
- `ShotLead = 0.125`：约等于房主 50 FPS 下 6 帧或一个 AK 间隔加一帧，覆盖 GunLoop 中的有序抖动（90/150 ms 成批）与房主每 23 帧 120 ms 的停顿；它同时是任何一发相对服务器时间轴所能提前的上限（长期射速不变）。两者都是候选值，实机网络下是否需要调整待用户反馈。
