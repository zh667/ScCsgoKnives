## 一、曳光：四个问题分别有来源、分别有验收

冒烟报告列的四条，逐条对上 `.vpcf` 里的算子，没有一条是"调参数"。

### 1. 起点：从画面上的枪口出发，不再从眼睛

第一人称武器用的是 CS2 自己的 viewmodel 投影（`viewmodel_fov 68` → 竖直 53.668°），
世界和曳光用的是游戏相机的投影。两者吃的是**同一个 view space**，所以一个 rig 点和一个
世界点落在同一像素，当且仅当它们的 view-space x/y 相差两个投影缩放系数之比。

`CsmcFirstPersonRenderer.RecordMuzzleFrame` 每帧记下该比值、placement 和逆 view 矩阵；
`TryGetMuzzleWorld` 用它把 `.vdata` 的 `m_vecMuzzlePos0` 换成一个世界点，
`SubsystemScGunBlockBehavior.Fire` 用这个点作曳光起点，方向指向命中点。

按构造误差为 0；仍然量了，因为比值取反会比什么都不做更差：

| 枪 | 修正后起点离画面枪口 | 原来的眼睛起点离画面枪口 |
|---|---|---|
| ak47 | **0.000 px** | 246.9 px |
| m4a1s | **0.000 px** | 231.0 px |
| m4a1s 消音 | **0.000 px** | 196.6 px |
| awp | **0.000 px** | 169.3 px |

（1400×1050，世界 FOV 60°。限值 3 px。）

无 cs2 profile、或该帧没画过这把枪时，回落到原来的射线原点——即旧行为，不是黑屏。

### 2. 材质：用的就是 CS2 那两张图

`C_OP_RenderTrails` 在两个系统里各有**两个**，纹理和混合模式不同：

```
materials/effects/spark.vtex            PARTICLE_OUTPUT_BLEND_MODE_ADD
materials/particle/sparks/sparks.vtex   PARTICLE_OUTPUT_BLEND_MODE_BLEND_ADD   (C_INIT_RandomSequence 第 4 帧)
```

`tools/cs2_tracer_texture.py` 从本机 CS2 导出的 PNG 烘出 `cs2_tracer_add.png` /
`cs2_tracer_blend.png`：**只做转置和重采样**，没有手画。

转置方向不是猜的，是从像素量出来的——两张图的长轴（64 行）都是"中间平台 + 两端斜坡"，
短轴（32 / 60 列）都是"窄芯 + 软肩"，所以行是沿曳光方向、列是横跨宽度：

```
spark.png        每行亮度 0.000 .. 0.183 平台 .. 0.000
                 每列亮度 0.000 .. 0.588 芯   .. 0.000
sparks_seq4.png  每行 alpha 0.008 .. 0.206 平台 .. 0.016
                 每列 alpha 0.001 .. 0.651 芯   .. 0.000
```

AK / M4A1-S 的 `C_INIT_RandomColor` **没有** `m_ColorMin/m_ColorMax`，即 Source 的默认白；
生成器现在把这个默认显式写出来并标 `ColorFromTexture: true`，所以 C# 不再"缺色就退回纯白"，
颜色本来就来自 spark 贴图。AWP 有真实色域 `[247,188,94]..[255,245,219]`，作为贴图的 tint。

### 3. 形状：半径来自文件，宽度在屏幕空间夹紧

```
                      粒子半径   pass A 半径系数   pass B 半径系数
assrifle (AK/M4)      1.0 in     0.5               0.75
rifle    (AWP)        2.0 in     0.5               0.65
```

关键的一项是 `m_bEnableFadingAndClamping = true` 下的 `m_flMinSize` / `m_flMaxSize`：
**屏幕空间**的夹紧。0.16.5 画的是固定 0.012 引擎单位半宽，不随距离夹紧，所以近处是一块白板、
远处细到看不见：

| 距离 | 0.16.5 半宽 | 0.16.6 ak47 半宽 | 0.16.6 awp 半宽 |
|---|---|---|---|
| 0.5 m | 21.8 px | **2.10 px** | **10.50 px**（并且已开始整条淡出） |
| 5 m | 2.18 px | 1.15 px | 2.31 px |
| 80 m | 0.14 px | **0.79 px** | **1.05 px** |

AWP 另有 `m_flStartFadeSize 0.015` / `m_flEndFadeSize 0.025`：按**未夹紧**的屏幕尺寸淡出，
所以贴脸飞过时它整条消失，而不是糊满屏幕。

唯一一处假设，已在代码注释和这里标出：`m_flMinSize` / `m_flMaxSize` 读作
**视口高度的比例、作用在半宽上**。文件没写单位；这是唯一一种读法能让 AK 的
0.00075..0.002 把 0.5 英寸的带子在整个有效距离上稳定在 0.8 ~ 2.1 px 半宽。

`m_flFinalTextureScaleU = 5` 记为未建模：烘出来的帧本身沿长轴已带一次头尾斜坡，
平铺 5 次会把这条斜坡沿曳光重复五遍。

### 4. 时间包络：按飞行进度，不是按拍脑袋

`C_INIT_MoveBetweenPoints` 把粒子从枪口控制点送到命中控制点，`C_OP_FadeAndKillForTracers`
在终点杀掉它。两个系统都没设 lifespan，`C_INIT_DistanceToCPInit` 只在 0..180 英寸内缩放
默认的 1 秒——20500 in/s 下 30 m 的一枪只飞 58 ms，若把 0.2/0.3/0.95 当"寿命比例"，
曳光到命中时还停在 StartAlpha=0。所以这三个数是**射线走过的比例**：

```
u <= 0.20   alpha 0            (所以 CS2 的曳光在枪口附近本来就看不见)
0.20..0.30  升到满
0.30..0.95  满
0.95..1.00  降到 0
```

长度：`trail = speed × TrailSeconds × LengthScale(离视点距离)`，上限 `m_flMaxLength`，
再乘 `m_flLengthFadeInTime` 的生长斜坡。所以一条新曳光是短的一截，逐渐拉长：

```
ak47/add   age 5 ms → 1.9 m,  10 ms → 3.8,  20 ms → 7.6,  40 ms → 15.2,  80 ms → 30.5 m (封顶)
awp/add    age 5 ms → 1.1 m,  10 ms → 2.3,  20 ms → 4.6,  40 ms →  9.1,  80 ms → 18.3 m
```

`C_OP_DistanceToTransform`（输出字段 10 = 轨迹长度）也照做：
ak47 x0.802 @1 m → x0.987 @100 m；awp x1.000 → x1.117。

### 一个必须先说清楚的后果：近距离本来就几乎看不到曳光

粒子在命中点被杀掉，所以曳光的存在时长就是 `距离 / 速度`。按 60 fps 数帧：

| 距离 | ak47 / m4a1s | awp |
|---|---|---|
| 5 m | 9.6 ms，**1 帧**（且这一帧 head 还在 u=0，alpha=0，等于不画） | 6.6 ms，1 帧 |
| 10 m | 19.2 ms，2 帧 | 13.1 ms，1 帧 |
| 20 m | 38.4 ms，3 帧 | 26.2 ms，2 帧 |
| 40 m | 76.8 ms，5 帧 | 52.5 ms，4 帧 |
| 80 m | 153.6 ms，10 帧 | 105.0 ms，7 帧 |

加上 `u <= 0.2` 全暗，**近距离对墙打，AK 每三发那一条曳光可能一帧都看不见**。
这是 `.vpcf` 本身的模型，不是省事：CS2 的曳光在枪口附近本来就是暗的。

`m_flStartFadeOutTime = 0.95` 意味着淡出只占最后 5% 的路程——20 m 时是 1.9 ms，
不到一帧。所以"整条突然消失"在这些距离上是 CS2 自己的行为，不是实现偷工；
真正被修掉的是 0.16.5 那种"尾巴越过命中距离才整条删除"的错误时机。

**因此实拍时请站远一点**（≥ 20 m）或对空打，5 m 对墙拍不到东西是预期结果。

### 曳光验收：`tools/cs2_tracer_selftest.py`

五个 case，全部 PASS。数字不是写死在测试里的，A 组逐项和 `.vpcf` 对：

```
A source     速度/最大长度/两个 pass 的纹理、半径系数、fade-in、min/max size 与 vpcf 逐位相同
B origin     四个枪口起点误差 0.000 px；并断言"眼睛起点"至少差 20 倍，否则修正没意义
C width      近处 <= 16 px、远处 >= 0.5 px、随距离单调不增、夹紧在两端都真的生效
D envelope   枪口处 alpha 0、中段满、命中前衰减；升 9 档降 4 档，不是开关
E textures    横向软边（两端 0.0% / 0.1% 峰值）、纵向头尾斜坡、截面不是平顶
```

C 组的"夹紧真的生效"是关键：只看结果数字会被巧合骗过，所以直接比未夹紧值和夹紧值。

## 二、阻塞 1：`Cs2Effects.Load()` 首次加载 NRE

属实，已在 VPS 复现：

```
02:28:19.938 WARNING: [ScCsgoKnives] Could not read AnimationData.cs2_effects.json:
Object reference not set to an instance of an object.
```

且**没有** `CS2 effects:` 成功行，而 loadcheck 仍报 70/70。

根因就是 review 说的：成功日志里写了 `TracerFrequency(kv.Key)`，它经 `Get()` 读
`s_guns`，而那正是当前静态初始化式的赋值目标，此刻仍为 null → NRE → 被外层 catch 吞成
warning。值是对的，加载状态是坏的。

两处都改了：

1. 日志改用 `kv.Value.TracerFrequency`，不再在静态初始化期间回调自身；`Get()` 也加了
   `s_guns is not null` 保护。
2. **加载状态不再靠日志推断**。`Cs2Effects` / `Cs2Weapons` / `Cs2Sounds` 各自公开
   `LoadError`（成功为 null），自检第一组就是 `load/effects`、`load/weapons`、`load/sounds`。
   "值对了"从此不等于"加载成功了"。

现在的输出：

```
[ScCsgoKnives] CS2 effects: ak47 muzzle0=(37.422,-4.938,-3.394) flash=1 tracer every 3; ...
load/effects = ok      load/weapons = ok      load/sounds = ok
```

## 三、验收要求 5：直接验收指定 scmod 内的 DLL

0.16.5 的验收跑的是工作树重编译的 DLL（`72f814bf…`），而实际发布包里的是
`02b70383…`——那一轮从头到尾没有打开过包。

改法是把断言搬进 mod 本体：`src/ScCsgoKnives/Animation/Cs2SelfTest.cs`（`RunJson()` /
`SoundTableJson()`）。于是同一份断言代码有两条入口：

* `tools/ArmPreview loadcheck` → 直接调用（工作树，仅供迭代）
* `tools/PackageCheck --scmod <path> --sha256 <hex>` → 先校验包哈希，从 zip 里取出
  `ScCsgoKnives.dll`，用独立 `AssemblyLoadContext` 加载，反射调用同一个 `RunJson`

`check_sound` 的工作树回退也删了。旧代码先在 zip 里找 `Assets/AnimationData/cs2_sounds.json`，
找不到就回落到 `src/` 下的那份——而那个文件**从来就不在包里**（它是内嵌资源），所以回落是
唯一走过的路径，等于一直在拿仓库的表去数包里的 OGG。现在 `check_sound` 直接调
`tools/PackageCheck`：cue 表从**那个 DLL 自己的内嵌资源**读，OGG 从**同一个包**里查，
两边不可能来自不同版本。

本版实测：

```
package        681de4438fdeeb798090afddd9aa0dcea56784e7b0fb5fd1c6d75fd36092d5a9
               259 entries, 46,965,206 bytes
包内 DLL       7cdf860540fb8284aa95025544d967ee7e91a29009f81adc42a63fdb623ae87b
107 / 107 checks PASS，其中 sound/coverage = 69/69 cues，表来自包内 DLL，52 个 OGG 同包
```

哈希不符时直接拒跑（exit 3），已实测。

## 四、阻塞 2：Windows 编码 / 返回码 / 吞 stderr

属实，六处 `capture_output=True, text=True` 都没有 `encoding=`，四处直接 `.stdout` 无保护，
多处不查返回码。

不逐点打补丁，改为一个共用入口 `tools/cs2_run.py`：UTF-8 + `errors="replace"`、必查返回码、
失败时把命令和子进程 stdout/stderr 一起抛出。全部 CS2 工具改走它；
其余老工具（chainfit / golden_m9 / preview / holdcompare / validate_shaders / trace）
最小改动补上 `encoding="utf-8", errors="replace"`。

这一改立刻抓到一个真 bug：`durations` 模式输出的是 JSON **数组**，而第一版 helper 只认
`{` 开头的行——`cs2_placement_selftest` 因此报错。已修（`{` 或 `[` 都收）。

Windows 命令示例一律 `python`，`docs/cs2-0.16.4-handoff-to-windows-2026-09-05.md`
顶部已加"已被取代"横幅。

## 五、阻塞 3：`arms_evidence` 的绕过口子

属实。旧代码只在 `method == "loadout_difference"` 时才看数字，所以
`{"method": "anything"}` 直接通过。

新的 `check_arms_evidence()`：

* `method` 封闭枚举，未知值直接 FAIL；
* 两个 loadout 各要 `team` / `agent` / `gloves` **和两张**截图，每张要 `path` + `sha256`；
* 四个文件必须互不相同（自己跟自己比什么也没测到）；
* `arm_roi` 必须是四个整数、非空、不倒置，且要能落在图里；
* **统计量由 checker 从已哈希的图重新算**，用的就是探针自己的 `compare_set`；
  manifest 写的数与重算不符（含手填、含负值、含改口的 verdict）一律 FAIL；
* 重算结果为 `inconclusive` 或 `different` 时不放行，并说明该识别哪个 agent。

上一轮的九个反例是临时脚本跑的，跑完就没了——一个只在能过的数据上跑过的验收器，

**哪一项**该挂、**因为什么**挂：

`max <= 2/255` 会看走眼的那类情形的反面例子。

## 六、方法问题 4：`--compare` 的阈值换成实测基线

旧判据 `max channel delta <= 2/255` 背后没有东西：CS2 不是逐位确定的，这个阈值既可能被
噪声打挂，也可能放过一个恰好很小的真实差异。

新协议要四张图：同一 loadout 拍两张（A1/A2、B1/B2），同图同枪同 clip 同 tick 同 cvar。
同 loadout 的两对就是**基线噪声**，跨 loadout 的差异只有落在基线之外才算数。

每对都报完整分布：mean / p95 / p99 / p99.9 / max / 超阈值像素比例。判据：

```
independent    跨 loadout 的 p99.9 <= max(基线 p99.9 + 1, 2) 且 mean <= 基线 mean + 0.5
different      超出上面
inconclusive   基线自己的 p99.9 > 8——场景在这块 ROI 里就不可复现，什么也不能归因于 loadout
```

`--compare` 保留单对用法，但它现在**明确拒绝下结论**（`verdict: no_baseline`）。

## 七、顺带修掉的一个真 bug：KV3 解析器吞块

写曳光提取时发现 `weapon_tracers_assrifle.vpcf` 解析出来**没有 m_Operators、没有 m_Renderers**。

原因在 `tools/cs2_kv3.py`：多行字符串的记号写成了 `""(?:.|\n)*?""`（双引号），而 KV3 的多行
字符串是**三引号**。`.vpcf` 里到处是 `m_NamedValue = ""`，于是每个普通空串都被当成多行串的
开头，一路吃到下一个空串，整块整块地消失。

修好后重跑全部生成器，只有 `cs2_effects.json` 变了，且都是"原本读不到、现在读到了"：
M4A1-S 消音火光的 `FadeOut 1.0`、`Drag 0.15`、`RadiusScale 2.0` 和三张贴图，之前全是空。
`cs2_bone_map.json`、三份 `.cs2.animation.json`、`cs2_weapons.json`、`cs2_sounds.json`
以及 22 把刀的 `.csmc.animation.json` **逐字节未变**。
