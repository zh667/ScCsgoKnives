# 1.3.0 全量：信标、模型菜单及人物重载卡顿修复

后续：当前输出全量已追加小队性能诊断，本文包哈希保留为该轮基线；资源和动画缓存不变。参见 [小队卡顿诊断](release-crowd-diagnostics-1.3.0-2026-09-26.md)。

日期：2026-09-26。用户报告手机信标召唤、NEO“更换模型”及部分重进世界卡死，电脑同位置也会明显停顿；授权修复并仅交付新的全量包，并要求参考本地其他模组的召唤实现。本次沿用公开版本 1.3.0，不替换轻量包，不安装到游戏或修改玩家世界。

## 已复现的瓶颈

旧 CT/T GLB 各约 41 MB，分别含 170 个动画、43,129/40,516 条通道。API 1.9.3.1 的 GltfAnimationConverter.ConvertSamplerByPath 在每个采样点重新 CreateCurveSampler(true)。原模型第一次经 ContentManager 加载时会同步执行这批转换。

信标的 DatabaseManager.CreateEntity → ComponentTacticalModel.Load 与 NMM 的 GetRes → ContentManager.Get<Model> 最终读取相同人物资源。NMM 模型列表为各模型建立预览，因此仅打开“更换模型”就可能触发两个角色加载。存档里保留 CT/T 同伴或玩家外观时，冷启动重进世界也会重新触发该路径。这里复现的是长时间同步解析和大量临时分配，不是已证明的线程死锁；不能据此排除其他模组造成的独立卡死。

读取了用户 Mods 目录中的尸鬼与命令方块 DLL：召唤也使用 CreateEntity、设置位置、AddEntity，没有必须照搬的异步召唤机制。尸鬼模型主要为较小的 DAE（最大约 582 KB）；不能把不同资源的加载成本等同。仅提取到开发临时目录进行静态调用检查，未执行或修改这些第三方 DLL。

## 修复方法

1. 打包前使用同版本原生 GltfLoader 生成实际运行时动画采样，写入每个角色的 .scanim。逐项校验所有片段、通道、时长和采样数组，CT 1,496,147 个、T 1,408,328 个采样键保留。
2. GLB 保留节点、骨骼顺序、蒙皮、模型几何、材质、原分辨率图片；移出已烘焙动画及未再引用的数据，保留一个小型缓存标记。所有存活 accessor 和 bufferView 数据检查一致，未降低全量画质。
3. ComponentTacticalModel.SetModel 在建立动画控制器前绑定缓存；ScAgentActions 构造时同样处理 NMM 玩家及列表预览。缓存随 ContentManager 的 Model 对象复用，重复召唤/预览不重复解析。
4. 读取是有界且原子发布的；缺失、损坏、骨骼不匹配会明确失败，不发布半套动画。读取不关闭 ContentManager 所有的共享流；失败后可重新读取正确缓存。不存在后台线程创建 GPU 资源。

不改变敌队规模、生成位置、信标消费事务、阵营/实体名、外观键、NPC AI、武器平衡或存档字段。前一版官方 NekoMeko 0.0.0.0 / 历史本地 1.0.0.0 的程序集兼容处理保留。

Windows API 1.9.3.1 原生 CPU 加载，一角色一个独立进程。新值包含几何 GLB 解析与缓存读取，不包含首次纹理 GPU 上传。

| 角色 | 旧 GLB 解析 | 新 GLB + 动画读取 | 旧解析累计分配 | 新加载累计分配 |

| CT | 19,631 ms | 153 + 124 = 277 ms | 16,090,909,112 B | 38,802,096 B |
| T | 17,501 ms | 168 + 127 = 295 ms | 14,653,262,984 B | 38,444,848 B |

累计分配是整个操作产生的临时对象总量，不是同时占用 15–16 GB 内存。桌面数据不能当作手机帧率或耗时保证。
