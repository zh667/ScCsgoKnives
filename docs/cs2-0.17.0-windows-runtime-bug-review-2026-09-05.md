# ScCsgoKnives 0.17.0 Windows 实机缺陷复核

日期：2026-09-05  
性质：Windows 实机日志与当前源码交叉审查  
结论：0.17.0 的 CS2 刀具基础渲染可用，但动作选择仍以旧 CS:MC 动画表为准，导致 CS2 路线缺少的动作别名静默回退 idle。特殊切刀、检视偶发无动作、切刀后立即检视无效均已确认。

## 2. 缺陷一：特殊切刀直接跳到完成姿势

### 现象

蝴蝶刀、骷髅匕首、流浪者匕首等刀有时不播放特殊切刀，直接显示切刀完成后的 idle 姿势。

### 根因

`src/ScCsgoKnives/Animation/KnifeAnimationController.cs:63` 仍然使用旧资源判断并随机选择：

```csharp
string deploy = !KnifeQa.Active
    && CsmcKnifeRig.HasClip(variant, "deploy2")
    && s_random.Next(2) == 0
        ? "deploy2"
        : "deploy";
```

但 0.17.0 的 CS2 JSON 没有收入这些 `draw2`，也就没有 `deploy2` 别名。`src/ScCsgoKnives/Animation/Cs2Rig.cs:157-165` 的 `ResolveOrIdle` 会在动作解析失败后静默回退 idle，所以视觉表现正是“直接显示切完后的姿势”。

### 受影响范围

旧 CS:MC 资源存在 `deploy2`、但当前 CS2 资源缺少 `deploy2` 的刀共有 7 把：

| 内部名 | 刀型 | CS2 Source 中已发现但未使用的动作 |
|---|---|---|
| `butterfly` | 蝴蝶刀 | `draw2_butterfly` |
| `canis` | 流浪者匕首 | `draw2_canis` |
| `cord` | 系绳匕首 | `draw2_cord` |
| `kukri` | 廓尔喀刀 | `draw2_kukri` |
| `outdoor` | 求生匕首 | `draw2_outdoor` |
| `skeleton` | 骷髅匕首 | `draw2_skeleton` |
| `ursus` | 熊刀 | `draw2_ursus` |

本次日志中共有 112 次刀具 Draw。把控制器选出的 CSMC 别名与 CS2 JSON 的别名集合交叉核对后，有 33 次必然回退 idle：

```text
butterfly deploy2  22
canis     deploy2   1
outdoor   deploy2   6
skeleton  deploy2   3
ursus     deploy2   1
```

`cord`、`kukri` 本次只随机到普通 `deploy`，但按相同逻辑同样是潜在必现项。

日志原文示例：

```text
10:27:45.181 INFO: [ScCsgoKnives] exact CSMC action=Draw, variant=17, asset=skeleton, clip=firstperson_draw2, duration=1s, ...
10:28:05.729 INFO: [ScCsgoKnives] exact CSMC action=Draw, variant=2, asset=butterfly, clip=firstperson_draw2, duration=1s, ...
```

而同一会话的 CS2 rig 清单只有普通 draw，例如：

```text
CS2 rig butterfly: clips=[draw_butterfly,idle1_butterfly,idle2_butterfly,lookat01_butterfly,light_miss1_butterfly,light_miss2_butterfly]
CS2 rig skeleton: clips=[draw_skeleton,idle1_skeleton,idle2_skeleton,lookat01_skeleton,light_miss1_skeleton,light_miss2_skeleton]
```

## 3. 缺陷二：G 检视偶发无动作

这是两个问题叠加，不只是用户按键过快。

### 3.1 旧控制器选择了 CS2 未打包的检视别名

`KnifeAnimationController.TriggerInspect` 根据旧 CSMC 表从 `inspect / inspect2 / inspect3` 中随机选择。当前 CS2 JSON 通常只收入 `inspect=lookat01_*`，挑中 `inspect2/3` 后仍由 `ResolveOrIdle` 静默退回 idle。

受影响 10 把：

| 内部名 | CSMC 可选别名 | 当前 CS2 可解析别名 | 当前未收入的 CS2 动作 |
|---|---|---|---|
| `butterfly` | inspect, inspect2, inspect3 | inspect | lookat02, lookat03 |
| `canis` | inspect, inspect2 | inspect | lookat02 |
| `cord` | inspect, inspect2 | inspect | lookat02 |
| `css` | inspect, inspect2 | inspect | lookat02（另有 draw/transfix 变体） |
| `falchion` | inspect, inspect2 | inspect | lookat02 |
| `outdoor` | inspect, inspect2 | inspect | lookat02 |
| `skeleton` | inspect, inspect2 | inspect | lookat02 |
| `stiletto` | inspect, inspect2 | inspect | lookat02 |
| `talon` | inspect, inspect2 | inspect | lookat02 |
| `ursus` | inspect, inspect2 | inspect | lookat02 |

本次日志记录 70 次 `action=Inspect`：

```text
能解析到 CS2 检视动作：36
选择 inspect2/3 后回退 idle：34
```

主要样本：

```text
butterfly inspect  成功 4；inspect2 失败 4；inspect3 失败 6
canis     inspect  成功 5；inspect2 失败 8
skeleton  inspect  成功 3；inspect2 失败 8
talon     inspect  成功 5；inspect2 失败 5
```

日志示例：

```text
10:23:18.936 INFO: [ScCsgoKnives] exact CSMC action=Inspect, variant=2, asset=butterfly, clip=firstperson_lookat03, duration=4.867s, ...
```

此时 butterfly 的 CS2 rig 没有 `lookat03_butterfly`，所以实际画的是 idle。

### 3.2 快速连按会不断重置已经成功的检视

`IsBusy` 只包含 Draw、Reload、Attach、Detach，不包含 Inspect。每次有效 G 都会重新调用 `Start()`，重置 `StartedAt`，因此快速连按会把动画持续压在第 0 帧附近。

本次日志中同一把刀连续启动检视的最短间隔约 0.17 秒，例如 canis 出现 0.174、0.187、0.173 秒连续重启；butterfly 和 skeleton 也有约 0.19 至 0.22 秒的重启。

因此“慢一点才能看到检视”有两个原因：

1. 慢下来后，成功选中的 inspect 有时间进入可见帧；
2. 多试几次后，随机选择终于落到 CS2 确实存在的 `inspect`。

## 4. 缺陷三：刚切刀按 G 没效果

`src/ScCsgoKnives/Animation/KnifeAnimationController.cs:151-155` 将 Draw 视为 Busy；`TriggerInspect` 在 Busy 时直接返回 `true`，没有播放、没有排队、也没有失败反馈：

```csharp
if (IsBusy(model)) return true;
```

所以该行为已由源码确认。

特殊切刀缺失时问题更明显：画面已经回退到 idle，看起来已经切完，但控制器仍按旧 CSMC `deploy2` 的时长维持 Draw 状态，期间 G 继续被静默消费。

## 6. 另外两个代码/日志缺陷

### 6.1 KnifeProfile 没有写入调参文件模板

`KnifeTuning` 声明了 `KnifeProfile`，解析器也能读取，但 `KnifeTuning.Serialize()` 在 GunProfile 前后没有输出 `KnifeProfile`。Windows 当前这一行是手工补入的。调参文件下次因版本戳变化被重写时，它仍可能消失。

0.17.0 交接中“首次运行会重写并产生 KnifeProfile”的说法不成立。

### 6.2 重复 Drawable 注册

最新会话仍有一次：

```text
10:23:10.710 ERROR: SubsystemDrawing: Drawable [Game.SubsystemScGunBlockBehavior] already added.
```

源码在 `SubsystemScGunBlockBehavior.Load()` 中手工 `AddDrawable(this)`，而当前引擎/项目加载流程显然已经注册过一次。它没有导致本轮崩溃，也不解释刀动画问题，但属于真实错误，应修正或加可靠幂等保护。

### 6.3 kukri 旧手臂警告不是当前 CS2 手臂故障

日志：

```text
kukri has a degenerate left forearm (0.291); left arm disabled.
```

它来自 `BuildLeftArmUsable()` 对旧 CSMC rig 的启动期预计算。CS2 路线通过 `DrawCs2Arms()` 绘制真实蒙皮手臂，不读取该 usable 表。本轮用户也未看到 kukri 手臂异常，因此目前按无关日志噪声处理，不应误判为 CS2 左臂被关闭。

## 7. VPS 侧修复要求

### P0：动作别名与资源完整性

1. 将 7 把刀的 `draw2_*` 收入 `.cs2.animation.json`，分别声明 `Alias=deploy2`。
2. 将上述 10 把刀需要的 `lookat02_*`、蝴蝶刀的 `lookat03_butterfly` 收入 JSON，声明 `Alias=inspect2/inspect3`。
3. 控制器在 `KnifeProfile=1` 时必须查询 `Cs2Rig` 的别名可用性和实际时长，不能继续只查 `CsmcKnifeRig`。
4. 建议新增 `Cs2Rig.HasAlias(asset, alias)`，动作选择只从当前 profile 真正可解析的别名中抽取。
5. 对非 idle 动作禁止 `ResolveOrIdle` 静默降级。至少要记录：requested alias、resolved clip、是否 fallback；最好让缺失别名在自检阶段直接失败。

### P0：输入状态机

1. Draw 期间按一次 G 应记录一个 `PendingInspect`，在 deploy 完成后自动开始；不要静默消费。
2. Inspect 正在播放时再次按 G 不应重新将动画时间重置为 0。可选择忽略重复输入，或只保留一个 pending 请求。
3. 只有真正开始检视时才显示检视提示/返回成功，Busy 时不能伪报已处理。

### P1：回归和可观测性

1. 增加全别名一致性测试：旧控制器可能选择的每个刀具 alias，在 `KnifeProfile=1` 时都必须能解析为 CS2 clip。
2. 强制覆盖 `deploy2`、`inspect2`、`inspect3`，不能依赖随机测试。
3. 运行日志增加一条轻量动作映射，例如：

```text
CS2 action: asset=butterfly requested=deploy2 resolved=draw2_butterfly
```

4. 单独统计 arms skin、weapon skin 和 combined skin；日志必须包含实际刀网格顶点数。
5. `KnifeTuning.Serialize()` 补写 `KnifeProfile`。
6. 排查/移除 `SubsystemScGunBlockBehavior` 的重复 Drawable 注册。

## 8. 修复后的 Windows 最小验收

不需要再跑 22 把完整长测。VPS 离线断言通过后，Windows 做以下定向回归即可：

1. 7 把 `deploy2` 刀各切入约 10 次，确认普通/特殊切刀都实际播放，不出现直接 idle。
2. 10 把多检视刀各按 G 约 5 次，所有按键都应启动可见动作。
3. 在 deploy 期间按一次 G，确认 deploy 完成后自动进入检视。
4. 检视期间快速连按 G，确认当前检视不会持续被重置到第 0 帧。
5. 补测 `bayonet`、`bowie` 的 deploy、idle、inspect、左右键挥砍。
6. 玩约两分钟，回收新的 arms / weapon / combined CPU skinning 数字及错误日志。
