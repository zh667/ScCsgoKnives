结论：新 Zstd 分体包已在该 Android 手机上成功加载，连续五次五人敌队召唤全部成功，动画缓存复用有效；仍有首用资源尖峰和密集 NPC 的持续低帧率。下一步优化应重点放在人物动画/骨骼、控制器分配和按需准备枪械资源，而非继续压缩包体。本文是日志分析，不修改生产代码或交付包。

## 哪些优化已经生效

1. CT/T 动画在加载阶段完成：609.52 + 534.47 = **1,143.99 ms**；全部 7 项预热合计约 **1,572.63 ms**。这是读取、解码、校验、原生对象构建等合计，不是单独 Zstd 时间。
2. 召唤时 AnimationCache 每队约 0.01 ms、汇总分配为 0；没有再次昂贵转换或解压全部人物动画的证据。后续五人队的创建集中在 24–27 ms，但在 60 Hz 帧预算下仍可能贡献一帧可见停顿。
3. 稳态 WeaponBuild、WeaponResolve 已很小。14:01:07 窗口二者共约 **0.1203 ms/帧**；WeaponBuild 分配为 0。GPU 武器提交继续走已有静态缓冲路径，未出现回退警告。
4. AnimationSample 在首窗口少量编译后，后续汇总分配均为 0。当前问题不能概括为“动画采样仍每帧创建大数组”。

## 剩余重点，按用途分开

### 持续低帧率：人物动画、骨骼与未覆盖的引擎工作

以 14:01:07 的稳定高负载窗口为例，没有新召唤，资源已热：

| 可分开的作用域 | 每帧耗时 |
|---|---:|
| Animate：整个人物动作处理 | **12.55 ms** |
| Bones：绝对骨骼变换 | **8.91 ms** |
| Extras：人物附加绘制/武器准备 | 3.87 ms |
| WeaponSubmit：武器提交 | 3.18 ms |
| EnemyAI：本 mod 敌人 AI Update | 1.82 ms |
| Director：调度 | 0.011 ms |

以上选定范围合计约 30.35 ms/帧；日志整帧 CPU 墙钟为 59.29 ms，尚约 **28.94 ms/帧没有归入这些范围**。这不是精确的全引擎互斥剖析，尚包括引擎人物蒙皮/提交、地形、物理/寻路、其他子系统、驱动等待等未知成本。GPU 未测量，不能据 engineCpu 接近 engineFrame 就断言全部纯 CPU 计算或 GPU 无关。

源码线索：ComponentTacticalModel.ProcessBoneHierarchy 每次遍历全部骨骼，CT/T 各 580/572 个，包含整套武器辅助骨骼；ScAgentActions 仍对上半身覆盖、动作混合执行逐骨骼处理。

优先候选：

- 为当前人物/手持武器编译有效骨骼集合，缓存静态分支；按实际皮肤影响、附件/枪械插槽、当前动作、父链闭包、死亡姿态确定，不能直接删除未手持枪的所有骨骼。
- 缓存可重复使用的动作绑定与静态握持姿态；保留每个实体独立时间、动作事件和切换状态。
- 再考虑远距离人物的视觉更新分级，保持近处、受击、开火/换弹和 AI 逻辑更新；必须检查停顿、插值与脚底接触。当前日志缺距离/可见数，尚不能量化该方案收益。
- 给人物蒙皮、实体物理/寻路、地形和渲染提交补充低频分项，先归因未覆盖的约 29 ms。AI 当前已分时感知/寻路，单看 EnemyAI 并非头号瓶颈，但它不包含引擎实际执行寻路/物理的全部代价。

### GC 和内存：控制器分配值得继续追

同窗口 AnimationUpdate 在 3,829 次调用中分配 **22,656.2 KiB（约 22.13 MiB/10 秒）**，约 136.48 KiB/帧、5.92 KiB/调用。采样本身为 0。这把调查范围指向原生控制器更新、状态规则与过渡快照；尚无分配栈，不能认定其中某个具体方法就是全部来源。

日志共 221 次 Gen0、3 次 Gen1、3 次 Gen2；这些是同一进程的代数计数，不能把三项直接相加当独立暂停次数，也没有 GC 停顿毫秒数。14:01:30 完整 GC 附近托管堆从 760.2 降到 650.3 MiB，随后升到 812.4 MiB，后七窗口没有 Gen1/2。因此不能认定泄漏或把全部内存归给本 mod。GC.GetTotalMemory(false) 的单位实际是 MiB，且不包括 Android 原生/GPU 完整内存。

CT/T 动画预热累计分配约 **102.64 MiB**，值得拆分解压临时缓冲与持久动画数组；它不是常驻内存或峰值。先做对象/缓存计数、进出世界前后相同阶段采样、长帧时间戳与 GC 增量关联；不要为“立刻降内存”每几秒强制 GC。

### 首次卡一下：只准备本次要出现的枪

前两窗口 WeaponResolve 单次最大 **80.52/85.45 ms**，对应 m4a4/deagle；WeaponBuild 最大 **25.50/86.86 ms**，对应 scar20/ak47。结合源码，前者包括首次颜色贴图加载/上传，后者包括首次 NPC 缓存读取/解码与几何对象构建。它们是已证实的首用热点，但不等于那个 1.38 秒整帧全部来源。

后续适合在确定小队装备后，按短时间预算准备该队所需的贴图、几何、GPU 数据，并去重共享资源；纹理和 GPU 操作继续留在主线程。若引入“准备好后一次加入小队”，保持原子生成/失败回滚，允许短准备延迟。不要一次预加载所有枪皮、全武器质量资源，避免手机启动和内存代价反弹。

要分别记录 CacheDecode、CacheParse、TextureLoad/Upload、BufferUpload 以及命中率；当前 WeaponBuild 汇总无法证明其中多少是 Zstd 耗时。

## 一条独立功能异常

14:02:27 的唯一 WARNING 表示 **烟雾弹 kind=2** 在 12 秒内没有静止支撑，速度仍约 0.85，因超时移除而没有生效。源码是既有防止悬空无限存活的保护；日志不足以确定是坡面、碰撞、卡缝还是低帧率下的落地判定。应单独检查连续碰撞/支撑稳定判定，不能简单改成到点强制空爆，也不能说这条警告导致了全程卡顿。

## 建议下一轮目标

先补足长帧事件与控制器/骨骼分项，再处理人物动画/骨骼无效工作及控制器分配；并行于同一优化目标的另一个方向是首用枪械的按需准备。保持当前模型轮廓和 512 颜色贴图，不再用压低资源质量作为这轮首选。作为区分基础渲染负载的对照，可在同一世界/同一人数/相近视角下只改一次视距或渲染分辨率，不能据当前单份日志承诺降设置或补丁能稳定 60 FPS。

后续手机记录应包含：无 NPC、固定 5/15/25 人各约 30 秒；首次与重复同装备召唤；明确换模和重进时间。NEO 模型选择与世界重进仍需单独覆盖。

本轮仅保存分析脚本、报告与证据，未修改或重新发布轻量/探员包。
