# 资源包压缩评估：WebP、音频与 512 贴图

2026-09-12。评估对象为当前 `ScCsgoResources-1.0.0.scmod`，329,598,982 字节，SHA256 `66fe182a3f83d01ff10ceb1dc6d00d0ebf5626f3ac30837eb9426751cbcb73eb`。本次仅在 E 盘独立目录生成候选文件，未替换正式资源包、核心、已安装模组或世界。最终重新核对原包哈希一致。

结论（已纳入用户后续“WebP 可以有损”）：建议将有损 WebP 作为正式候选。稳妥的低内存方案是常规贴图 512、颜色图 Q85、法线／ORM／透明图／图标无损，预计约 110.7 MB。极限方案是 512 全图 Q85，约 74.7 MB，但材质和特效表现仍需实机验收。当前 API 的音频解码存在实测兼容问题，音频暂保留现状。不能只凭在线转换网站显示“成功”就批量替换。

## “压到 512”是什么

一般是将 1024×1024 的贴图缩成 512×512 像素，像素数量由 1,048,576 变成 262,144，即原来的四分之一。不是 512 KB，也不是音频的 512 kbps。

WebP 是文件编码；512 是分辨率，两者可组合。无损 WebP 保留输入图片的像素，但把原图缩到 512 本身已经损失了细节，之后使用无损编码不会恢复那些细节。

本包有 342 张常规 1024×1024 图片。建议的 512 档只缩这些图片，小图标维持原样，并保留三个特殊大图：`env_specular_rgbm.png`（反射数据）、`muzzle_fire.png` 和 `muzzle_smoke.png`（枪口特效图集）。RGBM 不是普通颜色图，图集还涉及帧边界；不应对它们套统一缩放规则。法线缩图后重新归一化向量。

## 画面、内存与速度

无损 WebP：513 张全部经 API 1.9.3.1 的真实 `Engine.Media.Image.Load` 解码，与 PNG 的 RGBA 像素逐一比较一致，包括透明像素。不能把有损编码的 quality=100 当作无损，必须明确启用 lossless。

有损 WebP：压缩颜色图会出现细纹变淡、颜色串边；小图标收益很低，107 张图标现在在 ZIP 内仅占约 1.02 MB，不值得为它们额外损伤画质。法线图决定表面朝向，ORM 的 RGB 通道分别承载遮蔽／粗糙度／金属度等材质参数；普通照片式有损编码、色度抽样和通道误差会改变反光、凹凸和金属质感。因此这些数据图保持无损，不以“肉眼看这张彩色图差不多”验收。

512：皮肤细字、网点、纤维、划痕和磨损边缘会变软，第一人称近距离更明显。它不会减少枪械模型面数、改变动画帧数、武器物理大小或存档参数。

RGBA8 单张 1024×1024 的像素数据为 4 MiB，512×512 为 1 MiB，减少 75%；普通 WebP 解码后仍会上传为 RGBA8，所以只换编码不减少这部分显存。若全部图片同时展开，理论像素数据总量从 1,493,046,896 字节变为建议 512 档的 417,207,920 字节；实际游戏按需加载，还有 mipmaps、CPU 副本、模型和其它模组，不能把这个数字当成进程内存或帧率保证。

真实 Windows 引擎的纯图片解码抽测（内存输入，预热 2 次，再取 7 次中位数；三张大贴图）如下。没有包含文件读盘、GPU 上传或世界加载，不能据此宣称手机 FPS 改善百分比。

| 格式 | 三张大贴图的解码中位数范围 |
| --- | ---: |
| 原始 1024 PNG | 19.2～25.9 ms |
| 原尺寸无损 WebP | 31.8～35.2 ms |
| 512 PNG | 7.5～9.6 ms |
| 512 无损 WebP | 11.2～12.6 ms |

本机无损 WebP 的 CPU 解码开销高于 PNG，较小文件有助于下载和读取，但整体载入时间还需实机测试。512 降低像素数，在这组抽测中也降低了解码开销。

## 音频为何暂不批量转换

本包 347 段 OGG 在 ZIP 内占 3.88 MB，30 段 WAV 占 5.48 MB，合计 9.36 MB，只占整包约 2.84%。现有 OGG 已是有损压缩，再转码会进一步损失音质，整包收益有限。

所有 30 段 WAV 做了保留声道／采样率的本地 FFmpeg 测试：

| WAV 转换方式 | 新音频 ZIP 占用 | 理论节省 | 独立解码器 | 当前真实游戏引擎 |
| --- | ---: | ---: | --- | --- |
| Vorbis OGG，quality 4 | 0.69 MB | 4.79 MB | 30 段长度、声道、采样率均保留，音质有损 | 21 段单声道结构通过；9 段立体声中 7 段样本数减半，2 段抛异常 |
| FLAC，level 8 | 3.44 MB | 2.04 MB | 30 段 PCM 采样完全一致 | 仅 18 段与原 WAV 完全一致；9 段长度不足，另 3 段长度相同但数据不一致 |

因此“格式能被识别”并不等于实际音效完整。当前引擎的 `OggStreamingSource.BytesCount` 使用 `TotalSamples * 2`，没有乘声道数；`Ogg.Load` 又据此分配整段音频缓冲区。在本次生成的立体声样本上，表现为长度减半或字节数校验异常。FLAC 的原生加载路径也未完整还原上述有效文件，不能直接用它作为无损替换方案。这里验证到了编码文件与游戏解码结果的区别，没有修改引擎或当前音频。

把 21 段单声道 WAV 单独转 OGG也只节省约 1.05 MB；还要听检动作起音、枪声瞬态和循环接缝，目前不值得优先做。在线转换时还可能改变采样率、声道、响度或首尾静音；MP3 的延迟及循环处理要另外验证，AAC/M4A、Opus 也不能仅凭改后缀交给当前 Vorbis 读取器。

补充：抽样的旧 `bf1_kill_confirm.ogg` 本身也触发当前原生解码异常；当前击杀播报代码用的是 `bf1_kill_ding.wav`，不能据此宣称当前播报已经损坏。另有一个极短 OGG 重编码后采样数量发生变化，再次说明短音效不适合无条件反复转码。

## 工程兼容与建议

API 1.9.3.1 的 ImageReader、Texture2DReader 和 SubtextureReader 均支持 WebP。运行时大多按不带扩展名的资源路径加载，因此保留目录与文件主名可维持引用。纯资源编码／分辨率变化不需要改变枪型编号、涂装编号、实例号或存档 schema。

真正采用时仍要同步调整：核心的资源版本依赖、资源标记校验、包清单，以及 PackageCheck 等仍硬编码 `.png`／`.wav` 的检查。原版资源包 1.0.0 保留，不以同版本号静默覆盖成另一批数据；不要在包里同时放同名 PNG 和 WebP，让读取优先级掩盖测试对象。

在用户接受有损的前提下，建议顺序：

1. 稳妥的低内存方案：常规贴图 512，125 张 RGB 外观图用 Q85，其余无损 WebP，预计约 110.7 MB，较现在减少约 66.4%。不把特效图集和反射 RGBM 一起缩小。
2. 优先保细节：上述混合编码保留原分辨率，预计约 205.0 MB；细节好于 512，但贴图显存不变。
3. 压缩优先：原尺寸所有图都用 Q85 约 93.1 MB，512 所有图都用 Q85 约 74.7 MB。并非引擎不能读取；两档的真实图片解码都通过，但普通有损会改变法线、ORM 等通道数值，不能只看颜色图就宣布所有材质无差别。用户可接受有损不等于已验收这些实际效果。
4. 音频保持现状，先解决实际解码兼容问题再讨论批量转换。原尺寸无损 276.5 MB、512 无损 133.1 MB 留作画质比较基准，不把无损当成本次硬限制。
