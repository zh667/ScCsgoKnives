# 1.1.0 玩家反馈（十项）：原因、可行性与处理建议

日期：2026-09-16。分析基线：`main / 712a10f`，当前源码与 1.1.0 全量、512 轻量共用的玩法逻辑。

同日追加第 8～10 项：电击僵直、可设置时间的 C4、掉落物大小。追加时玩法代码未变，已有七项文档提交为 `7bd3aed`。

本轮只分析并记录方案，没有修改功能、重新打包、安装模组或改动玩家世界。附件里的聊天文字是玩家反馈，不作为执行删档、降级或其他操作的授权。

## 先说结论

| 反馈 | 当前判断 | 能不能做、建议怎么做 | 风险 |
| --- | --- | --- | --- |
| 1. 设置还要二次点击 | 已确认：模组设置里放的是“打开设置”跳转按钮 | 可以直接显示设置内容；优先复用现有设置编辑器，保留保存/取消 | 中低，主要是返回导航和设置保存 |

| 10. CS 武器掉落物太小 | 枪械采用真实尺寸，小手枪仅约 0.2 格；其他类型另用缩放 | 可以按类别提高掉落显示大小，检查全部型号 | 中低，不必改物品数据或手持模型 |

第 1～5 项都能改善，不需要修改枪械编号或存档格式。第 6 项必须先确认文件占用。第 7 项不能靠删掉报错检查来“修复”。

## 1. 枪械设置二次跳转

**原因已确认。** `src/ScCsgoKnives/modinfo.json` 的模组设置页只有一个自定义控件。`ScGunModSettingsWidget.Initialize` 创建“打开设置”，点它才进入 `ScGunSettingsScreen`。所以玩家已经选了“CS 枪械”，仍需再点一次。

建议目标：从模组设置选择“CS 枪械”后，就能修改选项。保留现有准星预览、按键布局、绑定和保存/取消行为，不另做一套互不一致的设置。

实现首选：把现有编辑内容整理成可复用控件，嵌入 API 的 CS 枪械设置页。API 1.9.3.1 的通用设置页原生支持自定义 Widget，但已检查的页面实现没有直接指定任意 Screen 的导航接口；不是只改一下 JSON 就能跳过所有中间层。若采用自动跳转，要额外处理从设置返回时再次跳转的循环，不宜在控件 Initialize 中立即切屏。

验收：主菜单和游戏暂停菜单都能进入；保存生效且重启保留；取消恢复原值；进入布局/按键绑定再返回不丢修改；返回不会循环跳转；不改变其他模组的设置页面。

代码：`World/ScGunModSettingsWidget.cs:6`、`World/ScGunSettingsScreen.cs:10`（均相对 `src/ScCsgoKnives/`）。

## 2. 选中后直接制作，数量自定义

**现状已确认。** `ScWorkbenchSelectionDialog` 单击只预览，双击才调用下一页；`SubsystemScWeaponWorkbench` 再弹确认页；`ScWeaponCrafting.TryCraft` 每次只产出 1 件。

建议界面：

- 选中配件、刀或枪后，右下角固定显示“数量”和“制作 N 件”。数量可输入或用加减，附 1/10/100 快捷选择；100 只是快捷数量，不代表任何背包都放得下。
- 上方即时显示“需要 / 持有”，按 N 倍计算；等级、材料或空间不足时禁用制作，并显示具体原因。
- 材料区域宽屏按两行横向排列，可横向拖动；窄屏改为适合宽度的两列/纵向滚动，按钮固定，避免材料挤出界面。
- 点击制作后留在本页，刷新库存和材料；成功提示不再强制跳回菜单。
- 维修、涂装、装计数器、设置等级等操作保留各自规则，不套用“制作 100 件”。

**最关键的是交易规则，不是按钮。** 建议一次批量要么全做成，要么不扣料，不默默只做一部分。先按数量计算材料，再规划“扣料之后”的成品空间：材料刚好用完腾出的格子也应能用。最终提交前重新检查库存、等级和装配台可用性，数量运算检查溢出，防止连续点击、库存代理变化导致重复扣料。

不能简单循环现有 TryCraft 100 次：第 37 次失败时，前 36 次已成功，界面可能只显示失败，玩家不知道扣了多少。应使用同一份事务记录，精确跟踪每个格子的扣料和产出；无法立即回滚的补偿沿用已有恢复队列。创造背包的目录槽不等于实际可写背包槽，也要单独处理。

验收：1/10/100、自定义数量、非法输入、材料分散在多格、扣料后刚好腾格、成品跨多个堆叠、空间不足、连续点击、离开/拆掉装配台、代理背包、加入成品失败后退款。枪械仍空枪交付，不改变等级、弹量、皮肤或编号规则。

代码：`World/ScWorkbenchSelectionDialog.cs:91`、`World/SubsystemScWeaponWorkbench.cs:75`、`World/ScWeaponCrafting.cs:75`。

## 3. 自动堆叠：配件可以，独立枪械不合并

**直接原因已确认。** `ScWeaponCrafting.TryCraft` 扫描的是 `GetSlotCount(i) == 0` 的空格，找到以后只往那个格子放 1 件。背包里即使已有 3 个金属坯件，也不会优先补到 4 个；如果没有空格，即使旧堆叠还有容量也会拒绝制作。

五种配件的 `MaxStacking=40`，本身允许堆叠，是制作交付路径漏了合并。已有 `ScGunInventoryJournal.AddExact` 支持向相同完整物品值的格子加入数量并记录撤销，可以在此基础上修复。

建议：优先同值且未满的堆叠，再使用空格；超过 40 分到下一格；禁止把不同配件只按方块类型混在一起。优先和第 2 项共用产出规划，避免先做一套堆叠逻辑，再做一套批量逻辑。

**不能把“所有成品自动堆叠”理解为同型号枪械合并。** 枪械保存自己的弹药、耐久、涂装、击杀数、等级及实例引用；枪和刀当前容量均为 1。保留容量规则，不以改 MaxStacking 的方式处理本反馈。批量做 10 把枪应交付 10 个独立格子的枪。

验收例子：已有 39 个金属坯件，制作 2 个，应变成 40+1；已有未满堆叠、没有空格，制作 1 个应成功；堆叠满且没有可腾空格时，材料应不变。

代码：`World/ScWeaponCrafting.cs:83`、`World/ScGunRecovery.cs:147`、`Blocks/ScWeaponMaterialBlock.cs:11`；枪刀容量见 `Assets/ScCsgoKnivesBlocksData.csv` 的 MaxStacking 列。

## 4. 仅按钮/全屏开火已有基础功能

当前路径：CS 枪械设置 → 手机按键 → **触屏仅开火按钮射击** → 保存。

- 勾选：在移动设备的触屏输入模式下，阻止原版触屏攻击触发枪械；自定义开火按钮仍可用。
- 不勾选：允许原版触屏攻击输入。实际点击/长按行为仍遵循原版触控设置，并非触碰任意 UI 都会开火。
- 键盘、鼠标、手柄不因该选项而禁用。
- **例外：关闭自定义按钮总开关，或禁用布局中的开火按钮，会自动允许原版触屏开火，防止无键可用。** 这可能造成“我选了仅按钮，为何还会全屏开火”的困惑。
- 判断包含 Android/iOS 和当前触屏输入状态；电脑上用鼠标点击并不能验收移动端限制。

建议先改为“触屏开火方式：仅开火按钮 / 原版触屏开火（全屏操作）”，显示实际生效状态。若要严格实现“选了仅按钮就绝不回退”，可以在选择该模式时启用开火键，并在之后隐藏开火键时提示；这是后续输入行为调整，需验证，不能宣称当前已有严格模式。

验收：安卓真机的空白视角区、开火键、背包、菜单、多指移动+开火；关闭开火键和总开关；切到蓝牙/USB 手柄；长按跨切枪、暂停恢复不能意外发射。本次没有安卓硬件实测。

代码：`World/ScGunSettingsScreen.cs:110`、`World/ScMobileControls.cs:5`、`World/ScUiSettings.cs:167`、`World/SubsystemScGunBlockBehavior.cs:905`。

## 5. 材料显示“没有配方”

截图里的金属坯件等五种材料，配方确实存在于 `ScComponentCrafting.All`。例如金属坯件需要铁锭 12、煤 4；材料通过枪械台制作。

**“没有配方”来自查询系统与制作系统未接通：**

1. 材料方块的 `GetProceduralCraftingRecipes()` 明确返回空。其成本包含大数量材料，设计上不走原版九宫格配方。
2. 原版图鉴用 `CraftingRecipesManager.Recipes` 统计配方数量，没有登记便禁用按钮。
3. 本模组给刀、枪、枪械皮肤/计数器模板补了“装配配方”入口，但 `BeforeWidgetUpdate/AfterWidgetUpdate` 没有包含五种材料；现有装配配方页也只查 `ScWeaponCrafting.Find`。

所以截图这类情况不是随机少加载了一次配方，而是材料类型没有被该入口覆盖。不同入口、不同物品看起来会有区别；若玩家指的是枪械台内部也出现配方缺失，则还需要那一页的截图/日志，不能用本结论包办。

建议：将五种材料纳入同一查询入口，按钮写“枪械台配方”，显示真实配方、产出数量和制作地点。只提供查阅，不往原版合成系统塞一个便宜替代配方，避免绕过现有材料成本。

验收：五种配件逐一查看，原版图鉴和已适配的 RecipaediaEX 都能返回；切换材料/刀/枪，不能把配方串到另一个物品；第三方普通物品及全局配方页面不受影响。未知版本的配方模组另行确认，不承诺所有第三方浏览器自动兼容。

代码：`Blocks/ScWeaponMaterialBlock.cs:24`、`World/ScComponentCrafting.cs:11`、`Mod/ScCsgoKnivesModLoader.cs:134`、`World/ScAssemblyRecipesScreen.cs:24`、`World/ScRecipaediaBrowser.cs:6`。

## 6. 存档体积增长：备份是优先排查项，尚非现场定案

**已核实的机制：**

- 公测 1.0.0 的枪械记录格式是 schema 4；当前为 schema 6。
- 第一次读取旧格式时，`ScGunSchemaUpgrade.BeforeLoad` 在世界目录里写入完整备份：`ScCsgoKnives-gunschema-4-to-6-<时间>-<随机后缀>.snapshot`，校验成功后才允许继续。
- 本轮反编译了用户本机 API 1.9.3.1 的真实 `Survivalcraft.dll`：`WorldsManager.GetWorldInfo` 会递归累加目录内所有文件大小，**没有排除 .snapshot**。因此列表显示包括备份。
- 备份采用 ZIP 压缩，额外体积取决于世界内容。一个约 38 MB 的世界加上二十多 MB 的备份，列表显示 60 多 MB 是可能的；这只是解释示例，不是对截图的实测分解。
- 正常保存成 schema 6 后，下次进同一世界不再触发这条 schema 升级备份。代码排除了已有 `.snapshot`，不会把备份套进新备份里。
- 但若旧格式尚未成功保存、加载中断或又恢复了旧 Project.xml，下次读取仍可能新建一个带不同名字的备份。这里不能说“永远只生成一次”。跨世界导入等路径也可能有独立备份，需按名称区分。

**目前缺的证据：** 玩家反馈对应的完整世界目录/文件清单，以及最好有升级前的对应备份；只给两项列表大小不能区分备份、探索新增地形、其他模组数据或重复存档。以前提供的 `工业s6.scworld` 不能在未核对来源与时间的情况下充当这次增长的现场证据。

建议按以下顺序只读排查：

1. 退出世界后列出世界目录中的文件名、字节数、修改时间。
2. 分别合计 `.snapshot`、`Project.xml/Project.bak`、`Regions`/地形文件和其他文件。
3. 对比升级前后：如果新增量基本等于备份，说明主要是安全副本占空间；如果 Project.xml 或地形仍在每次退出后异常增长，再检查具体字段/文件。
4. 若方便提供世界导出包，先检查包里是否真的带了这些 `.snapshot`；缺少它们的导出不能单独证明现场没有备份。也可以提供原目录文件清单，不必先上传完整世界。

可以做的改善：升级时提示“已保存旧版完整备份，世界列表大小可能增加”，并显示备份位置；后续加只读的本体/备份空间说明。重复备份去重需要校验同一来源内容和已有备份完整性，不能只看文件名或旧 marker 就跳过备份。

不建议为让数字好看而自动删备份、关闭迁移备份或修改全局大小统计。把备份迁到目录外也不是单纯改路径：涉及 Android 存储权限、导出携带和恢复入口，风险高于提示。没有确认可靠的外部副本前，尤其不要删除下面第 7 项可能要用的升级前备份。

代码：`World/ScGunSchemaUpgrade.cs:38`、`:48`、`:103`。真实 API DLL 的大小统计摘录与哈希见同目录的 `player-feedback-evidence-2026-09-16.json`。

## 7. 新版玩过后换回 1.0，出现加载错误

截图可读到 `ScGunSaveGuard.Validate` → `SubsystemScGunBlockBehavior.Load`，并提示“枪械存档格式无法安全读取……已拒绝加载和保存”。这是**格式校验拒绝**，不是图片渲染错误或轻量资源缺失。

结合已确认的 1.0 正式包：旧版 schema 4 不认识新版 schema 6，拒绝加载符合现有保护。之前针对真实旧 DLL 的测试也已通过“拒读 schema6”和“预加载保护拒绝”两项。截图右侧截断了具体字段值，故不能凭图片直接断言这名玩家报错后缀必定是 `Schema=6`；完整日志可最终确认是哪项格式条件触发。

**升级兼容与降级兼容是两回事。** 当前能读取受支持的旧格式，不代表已经发布的旧 DLL 会认识未来的数据。只改当前源码也无法让玩家重新安装的旧 DLL 自动支持新格式。

玩家可选路径：

- 想保留新版游玩后的进度：使用支持当前世界格式的新版；1.1.0 全量和轻量使用同一玩法 DLL，二者互换不属于退回旧格式。
- 必须回 1.0：保留当前世界，使用升级前的**完整世界备份复制恢复成另一份世界**，搭配旧包及原先相应模组环境。进度回到备份时间点，新版期间新增的进度不会自动带回。
- 找不到升级前备份：先保留世界，检查 `.snapshot` 和升级日志中的备份路径，不要删枪械记录或强改 schema 数字。

不能采取的“修复”：取消保护、把 schema 6 改成 4、删除 GunRegistry 后让旧版重建、只恢复 Project.xml 却保留不匹配的世界其他状态。这些做法可能让实例引用、等级和恢复数据丢失，不能作为通用回退方案。

专门做降级转换器技术上可以研究，但不是本轮低风险修复：要定义 Lv31～50、成长进度抵扣、新刀皮、C4 以及新版状态在旧版如何处理；部分内容旧版没有对应物，不能承诺无损。若要兼顾后续新版游戏进度，优先留在新版。

另：已有审计指出“仅计数、不成长”世界的升级存在错误套用等级的独立问题，仍见 [迁移风险审计](migration-100-risk-20260915.md)。它和这张旧版拒读截图不是同一种问题，不能把拒读解释成该漏洞，也不能以正常成长迁移通过推导所有模式均无风险。

## 8. 电击枪命中未死目标，产生 2～3 秒僵直

**结论：可以做，但当前不是完全没有控制效果，也不能只把一个数字改成 3 就承诺所有模组怪物都会停止行动。**

已确认的现状：

- 枪械命中统一进入 `ScSurvivalBalance.Attack`。电击枪当前设置普通目标 `StunTimeSet=1` 秒，身体质量 `Mass>=200` 的目标仅 0.3 秒；普通枪为 0.1 秒。
- 同一个目标有共享控制间隔。一次符合条件的电击命中后，5 秒内后续攻击不能再次施加这套冲击/眩晕；普通枪/刀也使用这张控制表，所以先被其他武器命中可短暂阻止电击控制。代码在最终伤害确认前占用间隔，最终免伤的攻击也可能消耗该机会。
- 设置了 `AllowImpulseAndStunWhenDamageIsZero=false`：无有效伤害时不产生这条眩晕。模组免伤、无敌阶段、特殊防御可能挡掉它。
- 本轮反编译实际 API 1.9.3.1 DLL 确认：`Attackment.StunTarget` 在 `ImpulseFactor<=0` 时直接返回。`ScProjectileDefense` 为已适配的蓝鲸、巨龟、Kraken 把 `ImpulseFactor` 设为 0，防止击退；这会连带阻止原生眩晕。不能为恢复眩晕而直接取消这些生物的防御或强行击飞它们。
- 原生眩晕主要限制 `ComponentLocomotion` 的移动处理，不是暂停整个实体。原版追击攻击组件也有自己的命中处理；已检查的 Subnautica Kraken 漩涡组件有独立 Update。因此“停止走动”不等于“停止攻击、施法及所有动画”。

建议先明确玩家看得见的效果：实际造成伤害、目标存活时，短暂无法主动移动；若称为完整“僵直”，还应抑制目标本体在此期间发起的常规攻击。保留重力、落水、碰撞和其他来源的物理作用，不能每帧锁死坐标或把实体所有组件停掉。

建议参数为 **2.5 秒**（需求区间中值，尚未实现），对同一目标保留独立的电击控制间隔，例如 5 秒，按电击成功生效开始计算，不被普通子弹共用计时干扰。新的命中不逐次累加时长。当前高等级电击枪可约每秒充能一次，如果每枪刷新 3 秒，会把大怪永久控住，多人还会放大此问题；冷却应按目标计算，而不是只按射手计算。

兼容分层：

| 生物实现 | 可实现范围 | 限制 |
| --- | --- | --- |
| 使用标准 ComponentHealth/ComponentLocomotion 的生物 | 可复用原生眩晕限制主动移动，兼容性较好 | 仍要检查攻击路径；标准组件存在不等于所有自定义技能都受控 |
| 继承标准组件但增加特殊 AI/技能的模组生物 | 移动眩晕加已知攻击/技能适配 | 需按实际组件和版本核验，不按怪物名字猜能力 |
| 完全自定义移动、伤害或独立实体技能的生物 | 通过其公开控制接口或专用适配实现 | 无统一接口时不能保证完整僵直；已发射的弹丸/已有领域也不自动消失 |

控制应尊重友伤开关、死亡、无敌/明确免控等规则。对已知目标需要把“不击退”和“可眩晕”分离处理，而不是绕过免伤重新制造攻击。死亡、移出世界、世界退出时清理临时状态；若不保存短暂控制，则读档后解除，并清楚定义这一行为。不要永久覆写 AI 速度或删除其状态。

建议优先做标准生物和明确验证过的模组生物，未知生物保持原有伤害路径，不将“全部模组兼容”作为承诺。验收包括：普通动物、重型目标、飞行/水生生物、蓝鲸/巨龟/Kraken、另行提供的龙；命中免伤/死亡目标、连续电击、多人轮流电击、先普通枪后电击、已开始的攻击、退出重进。确认到期恢复且不会永久瘫痪，并区分不能移动和不能攻击。

代码：`World/ScSurvivalBalance.cs:35`、`World/ScProjectileDefense.cs:10`、`World/SubsystemScGunBlockBehavior.cs:1238`。实际 API 的眩晕条件摘录附于证据 JSON；模组技能参考本地既有 Subnautica 反编译资料，本轮未重新加载全套模组战斗实测。

## 9. 可由玩家设置引爆时间的 C4

**现有模组已经有 C4。** 本需求优先按“给现有 C4 增加安装前设时”分析，不必新增第二个完全相同的物品。若希望固定 20 秒款与另一款可编程炸药并存，也能做，但要另定名称、配方、创造栏和旧值兼容，工作量更大；本轮不擅自确定为两种。

现状：默认引爆时间 20 秒，安装约 3.2 秒。每颗已安装 C4 已保存 `Fuse`（总时长）和 `Remaining`（剩余时长），合法总时长为 1～300 秒。实际安装代码新建对象时直接使用默认值，没有玩家输入入口。因而在现有范围内设时，可以利用现有保存字段，**不必为此修改 GunRegistry 或枪械格式**。

建议交互：持有 C4 时打开“设置引爆时间”，输入秒数并给常用快捷值；手机通过明确按钮/设置入口操作，不能占用会与安装动作冲突的按键。建议 UI 范围先取 5～300 秒，默认仍为 20 秒，属于待实施建议。记住该玩家的下次安装默认值；开始安装时冻结本次值，完成后该颗 C4 使用自己的 Fuse/Remaining。以后改设置只影响下一颗，不能把地上所有炸弹一起改时间。

如果希望“每个背包物品提前编程，并在丢出/转交后仍记住不同时间”，现有未安装物品没有逐件时长字段，那是另一层物品数据设计，风险更高。最小方案是安装前选时、安装后逐颗独立保存。

**滴滴声处理必须一起设计：**

- 现有倒计时统一播放 `c4_beep2`、pitch=0，避免此前换到 `_10sec` 闷声音源的问题；安装按键音、最后警报及爆炸音是各自事件。
- 当前滴声间隔为 `0.1 + 0.9 × 剩余时间/总时间` 秒，即全程由约 1 秒逐渐加快。它对不同总时长可以工作，但 300 秒和 5 秒的紧迫感曲线不同，需试听，不能宣称自动等同 CS2。
- 最后 1.5 秒进入警报，不再发普通滴声；最后约 0.1 秒触发引爆提示。这些是绝对剩余时间，不能简单把整个音频拉长/压短，也不要通过不断降低音高表达加速。
- 暂停、睡眠/时间加速、卡顿、存档重进应以游戏计时为准；离线不应偷偷按现实时间扣完整倒计时。跨过多个滴声时跳过过期普通滴声，不能补播成一串爆音。
- 当前 `WarningPlayed/TriggerPlayed/BeepLeft` 不保存，读档后会重置；最后警报阶段重进可能重播提示。大时间步直接归零也会先爆炸而跳过末段音效。需定义恢复音频阶段的规则，避免重播完整警报、爆炸后仍滴声或人为延迟爆炸。已有数据足以推导大部分阶段；若新增可选保存字段需兼容缺失默认值，无须盲目升格式。
- 多颗不同时间的 C4 必须各自调度、按位置衰减；现有最多 16 颗限制保留。验收时也要听多颗重叠和走远后的音色/音量，不能把距离衰减误判成换样本。

验收：5/20/60/300 秒、空输入/负数/超范围；安装中改默认值；同时安装两颗不同时长；安装取消不扣物品；不同倒计时阶段保存重进；低帧率跨过最后阈值；暂停与时间加速；确认每颗只爆炸一次，沿用已有伤害/半径/安装动画。音效需要实际试听，单靠代码检查不能验收。

代码：`World/ScC4Charge.cs:7`、`:19`、`World/SubsystemScC4.cs:135`、`:189`。

## 10. 部分 CS 武器掉落物太小

截图中地面小物体确实很难辨认，但没有可靠型号、距离或现场版本信息，不能只凭这几像素认定是哪把枪，也不能把它直接归因于轻量贴图压缩。

**已检查出两套不同的缩放路径：**

| 类型 | 当前掉落绘制 | 影响 |
| --- | --- | --- |
| 可正常解析的枪械 | `ScGunDropRenderer` 绕过原版物品缩放，按第三人称装配模型的米制尺寸、scale=1 画出 | 步枪正常长，真实小手枪也真的很小；没有最小可见尺寸补偿 |
| 刀具 | 模型归一化最长边为 1，再接原版掉落 size=0.3 | 最长边约 0.3 格，薄刀侧面仍不易辨认 |
| 未投出的手雷等物品 | 归一化模型 ×0.65×原版 size=0.3 | 最长边约 0.195 格；飞行中的投掷物有另外的绘制路径 |
| 未安装的 C4 | 模型已转换成米制尺寸，又接原版 size=0.3 | 相对其自身米制世界模型缩小到 30%；已安装 C4 则使用 scale=1 |
| 缺记录/无法识别的枪或模板特殊路径 | 不一定进入正常枪械掉落接管 | 需要独立检查，不能通过猜型号来“修正”异常枪数据 |

真实 API DLL 的 `Pickable.Draw` 默认 `drawBlockSize=0.3` 已反编译确认。枪械专用 hook 只接管有效 `ScGunBlock`，没有统一接管刀、手雷、C4；不能改一个通用物品大小就认为全都一致。

| Glock-18 | 0.202 |
| P250 | 0.203 |
| Five-SeveN | 0.204 |
| 电击枪 | 0.248 |
| 沙漠之鹰 | 0.294 |
| MP9 | 0.563 |
| AK-47 | 0.948 |
| AWP | 1.363 |

这些是**既有检查测得的装配模型包围尺寸**，不是截图中的像素测量；既有测试测量的是 For 模型，另检查 ForDrop 的减面成功，并未逐枪比较减面后实际可见三角形的包围盒。当前 ForDrop 使用顶点聚类，没有统一缩小整个模型的操作；这不能替代对极细零件、所有皮肤路线及真实落地画面的验收。完整采样记录保存在证据 JSON。

可行方案：仅在掉落路径按类别设置倍率或最小可见尺寸。例如先试手枪/电击枪最长边至少 0.4～0.45 格、手雷至少约 0.3 格，长枪保持现有量级；这是待实机比较的建议值，不是已定稿的倍率。刀具要兼顾薄度与旋转角度，不能为了侧面每一帧都显眼就把整把刀放得过大。未安装 C4 单独校准，已安装 C4 不跟着放大。

只改变掉落物的显示变换，不改变第一人称、第三人称持枪、背包图标、投掷飞行模型、伤害范围或实际拾取逻辑。放大矩阵要围绕正确中心，计数器附件同步缩放；浮起高度随实际模型边界校准，检查地面、台阶、雪、水面、卡在方块中的物品，避免一放大就穿地或绕远处旋转。

后续验收覆盖：35 枪、原皮/皮肤/计数器、消音器两态、全部刀型与刀皮、6 投掷物、掉落 C4 与已安装 C4；全量/轻量两版；近处和中等距离、旋转正面/侧面、暗背景；普通原版掉落物不受影响。单纯放大不增加三角形数，但会增加一些屏幕像素覆盖，仍应观察多掉落物场景，不能承诺绝对零性能成本。

1. 先完善第 6/7 项说明与现场文件统计，保留可回退的完整备份。
