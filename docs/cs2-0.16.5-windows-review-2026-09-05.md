## 阻塞 1：`Cs2Effects.Load()` 每次首次加载都会产生一次假失败警告

直接运行工作树 DLL 和包内 DLL 都稳定复现：

```text
WARNING: [ScCsgoKnives] Could not read AnimationData.cs2_effects.json:
Object reference not set to an instance of an object.
```

但随后 70/70 又通过。根因在 `Cs2Effects.Load()` 的成功日志：

1. `s_guns` 由 `Load()` 初始化，此时尚未完成赋值；
2. `Load()` 已把三个 gun 填进局部变量 `loaded`；
3. 成功日志在 `Load()` 内调用 `TracerFrequency(kv.Key)`；
4. `TracerFrequency()` 通过 `Get()` 访问尚为 null 的 `s_guns`，触发 NRE；
5. 外层 catch 捕获异常并返回已经填好的 `loaded`，所以运行值仍然存在，loadcheck 也继续通过。

这不是“资源仍然没加载”，但它证明当前 loadcheck 会在加载器抛异常、输出失败警告时照样 PASS。

VPS 必修：

- 成功日志不要在静态初始化期间回调 `TracerFrequency()`；直接从 `kv.Value.TracerFrequency` 格式化，或在初始化完成后记录。
- `loadcheck` 必须把加载错误作为断言失败，不能只看最终字段值。建议加载器暴露结构化 `LoadSucceeded/LoadError`，或测试宿主捕获诊断并断言没有 `Could not read`。
- 修后直接运行必须出现 `CS2 effects: ...` 成功行，并且完全没有上述 WARNING。

## 阻塞 2：Windows 默认命令会让自测脚本自身崩溃

在这台 Windows（Python 3.11，系统默认 GBK/CP936）直接运行：

```powershell
python tools/cs2_runtime_selftest.py
```

复现：

```text
UnicodeDecodeError: 'gbk' codec can't decode byte ...
AttributeError: 'NoneType' object has no attribute 'splitlines'
```

临时设置 `PYTHONUTF8=1` 后才得到 70/70。本机没有可用的 `python3` 命令，Windows 文档中的命令也应写成 `python`。

VPS 必修：

- `subprocess.run(..., text=True)` 显式加 `encoding="utf-8", errors="replace"`；
- 对 `stdout/stderr is None` 做防御；
- 检查子进程返回码；
- 有加载器 WARNING 时不得静默 PASS；
- Windows 用法统一为 `python tools/...`，不要写 `python3 tools/...`。

`cs2_reference_check.py` 中调用 `dotnet run` 的地方也建议应用同样的编码与返回码处理。

## 阻塞 3：`arms_evidence` 仍可被任意字符串绕过

`check_hand()` 当前只要求 `arms_evidence.method` 非空；只有当 method **恰好**等于 `loadout_difference` 时才检查 `max_channel_delta`。

因此以下证据会绕过 agent/loadout 门禁：

```json
{"method":"anything"}
```

即使 method 正确，代码也没有校验报告中声称的：

- `loadouts_compared` 是否存在、是否至少两个不同 loadout；
- `arm_roi` 是否存在、坐标是否合法；
- `max_channel_delta` 是否为 0..255 的有限数（负数当前也会过）；
- 参与比较的两张图片、它们的 SHA-256，以及该数值是否由图片重新计算得到。

所以“checker 校验 method / loadouts / ROI / 阈值”这句话目前不成立。

VPS 必修：

- method 使用封闭枚举，未知 method 直接 FAIL；
- `loadout_difference` 强制要求完整的两份 loadout 描述、两张图片相对路径与 SHA-256、合法 ROI；
- checker 自己重新打开两张图片并计算指标，不信任 manifest 手填的 `max_channel_delta`；
- delta 强制为有限且在 0..255；
- 增加未知 method、缺 loadouts、缺 ROI、负 delta、图片哈希不符、手填 delta 与重算不符等负例。

## 方法问题 4：真实画面不应直接用“ROI 最大通道差 <= 2”作唯一门槛

当前 `--compare` 的正例只是合成图整体加 1；它没有覆盖真实 CS2 的相邻帧噪声、idle sway、TAA/抖动、曝光变化，也没有做配准。大 ROI 中只要一个像素变化超过 2 就全局 FAIL，极易误杀。

而且“只换 loadout”需要更精确定义：应保持同一把枪、同一 clip/tick、同一位置角度与光照，只换 team/agent/gloves；若枪或动画相位也变化，ROI 的差异不能归因于 agent/loadout。

建议 VPS 先扩展协议，再让用户采集：

1. 每个 loadout 拍两张基线重复图（A1/A2、B1/B2），先量本底噪声；
2. 固定同一武器、同一姿态/动画时刻；能暂停到同 tick 最好；
3. 做必要的亚像素/整数配准，或至少证明无需配准；
4. 报告 `p95/p99/p99.9`、均值和超阈像素占比，不用单个最大值作为唯一门槛；
5. cross-loadout 差异必须相对 baseline 显著，才可判定 loadout 有影响；若与 baseline 同级，只能判定“未观察到影响”。

这条是方法学修订，不代表现有包的手臂运行时错误；但在协议修订前，不应让用户反复重录。

## 仍有一处包级 provenance 缺口

`cs2_runtime_selftest.py` 通过 `ProjectReference` 重新编译并测试工作树 DLL，不是指定 `.scmod` 内的 DLL。`check_sound()` 在包里找不到松散的 `cs2_sounds.json` 时又回退到工作树源文件。因此当前默认流程不能证明“被验收包内嵌的声音表 == 工作树声音表”。

建议给 runtime selftest 增加 `--scmod <path> --sha256 <hash>`，自动把指定包内 DLL 放入测试宿主并测试；声音 cue 表也应从这个精确 DLL 的嵌入资源读取，再检查同一个包里的 OGG。
