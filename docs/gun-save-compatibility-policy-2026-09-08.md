# 枪械存档长期兼容规范：以 0.37.0 为基线

日期：2026-09-08（Asia/Shanghai）。用户要求将讨论完整落实为后续开发约束。

本文是兼容设计和发布要求，不代表所列保护均已实现。本次只更新文档，不修改运行时代码、不升级数据格式、不重新打包。实现基线为 `2e03167 / 0.37.0`，已公开发布的版本仍只有 0.28.2；本地完成或打包不等于公开发布。

## 1. 范围与玩家承诺

正常升级受支持的正式版本后，枪还是原来的枪，名称、图标、型号、弹量、消音器、耐久和充能状态按明确规则保留，玩家可以继续原世界。不能把“一背包问号，请新建世界”作为正式存档的常规升级方案。升级失败不得覆盖原存档或留下半迁移状态。

| 存档来源 | 长期处理规则 |
| --- | --- |
| 来源明确、未经内部测试版改写的正式 0.28.2 | 保留专用自动备份迁移入口；保留型号、弹量、消音器，首次初始化满耐久，不赠送弹药 |
| 0.37.0 基线及以后正式支持的数据格式 | 保持同格式读写兼容；发生格式变化时提供明确转换，保留已有状态，支持跨过中间发布版本升级 |
| 0.29～0.36 内部测试格式 | 不承担全面历史迁移，不依据位模式猜测，不成为正式兼容链的必经节点 |
| 不认识的未来布局/schema | 加载前阻止继续及自动保存，要求使用支持该格式的版本；不降级改写 |
| 损坏、混合或来源不明的数据 | 保留原数据和诊断信息，使用备份或明确恢复流程；不猜型号、不删除、不默认为满状态 |

0.37.0 是后续保护基线，即使目前尚未公开发布，也不再以“仍在测试”为理由任意改写其枪械数据含义。已被内部版误写成其他型号且没有原始记录的枪，不能可靠倒推，只能从可信备份恢复。

本文覆盖旧规划中对枪械“每版新世界、不做跨版本兼容、可直接换格式”的历史限制。其他批次仍自 **2026-09-08 00:22:15 +08:00** 起 BLOCKED；仅 M4 及其枪械数据保护范围有效，不据此恢复烟雾、第三人称或其他功能开发。ID 回收仍不在本轮范围内。

## 2. 冻结物品含义，优先扩展记录

0.37.0 的物品布局为 v5：低 6 位为型号，随后 10 位为实例 ID。ID 0 是满弹新枪模板，1023 是空弹新枪模板，1～1022 对应世界记录；第 16 位不是可随意复用的扩展位。完整物品值还包含方块内容和光照位，转换不得把裸 data 当完整物品写回。

世界记录保存弹量、消音器、精确耐久、最大耐久、修订号、充能等状态。新功能优先扩展世界记录，不重新编码每把物品。

- 枪型编号永久稳定，以现有 `GunSpec.FrozenOrder` 为基准；新增型号只使用未分配编号。菜单顺序、中文名、资源名变化不能改变保存编号。
- 删除或停用型号也不得把编号分配给另一把枪。保留旧编号的识别与明确恢复/替代路径，不能静默映射。
- 实例 ID 的含义稳定。记录排序、整理字典、序列化顺序变化不得重新编号或串接其他枪；ID 不能被另一把独立枪随意复用。
- 当前 6 位型号和 10 位 ID 有容量上限。超过容量属于需要方案和迁移的大改，禁止溢出、截断或偷偷占用格式位。
- 修改记录仍使用既有事务入口及持有者/恢复机制，不能为迁移后的日常操作另开直接写记录路径。
- 复制隔离、隔离记录、ID 分配水位、未完成物品补偿同样属于需要保存的完整性状态，格式升级不能丢弃。

## 3. 模组版本、物品布局与记录 schema 分离

| 版本信息 | 当前基线 | 何时改变 |
| --- | --- | --- |
| 模组版本 | 0.37.0 | 发布功能、修复、资源改动 |
| `GunDataLayout` | 5 | 物品位布局或其含义确实改变 |
| `GunRegistry.Schema` | 1 | 记录的保存结构或字段含义改变 |

修复维修扣料、修改伤害或动作通常只变模组版本，不改变另外两项。版本号不应随着每次打包机械递增。

现有 schema 1 严格要求每条记录恰好 7 个字段。不能直接追加字段却仍写 schema 1；应新增 schema 及转换器。原来不存在的属性可在迁移中补默认值，原来已经保存的属性不得因解析失败被当作缺省字段重置。

显式布局和 schema 优先于历史键推断。只接受明确支持的组合，禁止用 `>=5` 放行所有未来版本，禁止因存在 `GunRegistry` 就覆盖未知/旧布局戳。无戳格式只能通过明确来源专用入口识别；0.28.2 使用保存的模组身份和版本，不能伪造来源以强制迁移。

## 4. 转换器与状态保留

未来 schema 1 升 schema 2 的固定过程：读取已确认的旧结构，严格验证，在独立副本转换，保留已有字段，补新增字段，验证目标结构，再完整提交。以后升 schema 3 时保留前面的转换器，让跳版本玩家按链逐级转换，无须安装所有中间版本。

转换必须确定、可重试且不会重复给资源。迁移版本标记和结果共同保存；已经完成的转换不得再次满修、补弹或重置充能。若正常保存前退出，磁盘仍为源格式，重试应得到同等转换结果。

需要逐一核对的状态：型号、ID 引用关系、枪数、弹量、消音器、当前/最大耐久、充能剩余状态、记录修订关系、分配水位、隔离原文、待恢复物品及其持有者。两个相同型号但不同磨损的实例不能被合并。

新增“维修次数”可以初始化为 0；已有耐久不能初始化为满。0.28.2 补满耐久仅因为它没有自定义耐久，是专用入口的一次初始化。其旧版玩家级电击枪时钟不能准确映射每把枪，现有专用例外见 [0.28.2 实现记录](official-0282-compatibility-0370.md)，不能把此例外推广到已有实例充能的版本。

## 5. 平衡参数变化的旧枪规则

格式不变也可能发生语义变化。每次改动必须说明旧实例的处理方式，并验证只应用一次。必要时引入明确的平衡修订标记；不能让每次查询或读档反复换算。

| 改动 | 处理要求 |
| --- | --- |
| 伤害、后坐力、动作 | 使用新参数；不重置枪械保存状态 |
| 最大耐久 | 默认保持耐久比例；例如 750/1500 变为 1000/2000；保留报废为 0、满修为满，不意外复活报废枪 |
| 增大弹匣 | 保留现有弹量，不自动增加子弹；明确 ID 0 这类按配置求值的新枪模板是否需要在转换时实例化 |
| 减小弹匣 | 预先明确超额弹药如何退回；没有容纳位置时保留待领取/恢复权益或整体拒绝，禁止静默截断 |
| 充能时长 | 该次改动明确保持剩余秒数或比例；不能读档直接充满，仍按会话时钟规则保存剩余量 |
| 停用型号 | 保留旧编号与识别/恢复路径；不复用编号、不悄悄换枪 |

比例换算建议使用整数运算，明确取整方式并在实现时固定测试：损坏枪始终为 0；仍可用的枪不因取整变成 0；结果不超过新最大值。上述例子不是本次修改枪械寿命或弹匣的授权。

## 6. 整个世界的迁移与备份

1. 在正常加载、枪械使用及自动保存前识别源布局/schema，核实转换链和目标支持范围。
2. 在独立数据副本上预检数据和容量，盘点所有受影响的物品存储位置。
3. 对磁盘原世界创建完整备份并校验成功，才允许启用转换结果。地形、附属文件和其他模组侧文件均应保留；备份排除已有 snapshot，避免递归膨胀。
4. 在副本上完成全部转换并验证引用、数量、状态和版本标记，不能边遍历边改活世界。
5. 只有完整成功才把结果交给游戏加载；任一步失败，不启用部分转换，不允许继续游戏后自动覆盖来源信息。
6. 正常保存时物品、记录表、补偿状态和版本标记写在同一一致快照中。后台只能持有不可变的序列化快照。
7. 区分“内存转换完成”和“成功写盘”；保存请求发出、回调触发或完成信号不能单独证明写盘成功，必须核对引擎的错误路径。

备份只在实际需要迁移枪械存档时创建，不要求每次进世界备份。未保存转换结果就退出，再次进入可能重新迁移并生成独立备份，这是允许的。

未来通用迁移备份应包含来源/目标格式、UTC 时间和唯一后缀。当前 0.28.2 专用文件名仍为 `ScCsgoKnives-before-0282-<UTC>-<后缀>.snapshot`，无需为统一命名修改已交付逻辑。先写临时备份，关闭并校验后才标为成功，不覆盖已有备份，本次升级不得自动删除它的首次有效源备份。

日志和提示应包含来源/目标格式、迁移数量、失败原因、备份位置；不要记录无关隐私。玩家恢复时需配套兼容的模组版本，不能把世界备份等同于包含旧模组 DLL。

写盘失败必须保留有效备份和可诊断错误，不能宣称升级已安全落盘。系统断电/磁盘损坏的边界需实测和说明，不能用离线转换通过代替引擎实际写盘保证。

## 7. 未来格式与误降级保护

假设未来版本保存 schema 2，玩家误装只认识 schema 1 的包。正确行为是在正常加载/自动保存前拒绝进入，显示该世界需要支持对应格式的版本；原布局、schema、数据和来源信息保持不变。

仅保留未知记录子树、停用枪械或显示问号不够：其他保存路径仍可能把布局戳、来源版本和库存写成旧含义。必须验证未知显式布局不会被改为 4/5，未知 schema 不会被重写为 1。

这项保护需要在理解它的版本发布前实现并验证。未来代码无法改变玩家已经下载的旧 DLL，因此只能承诺已具备保护的版本会安全拒绝未知格式，不能宣称任意历史包均可安全降级。备份加匹配版本是恢复路径；自动反向降级迁移不在当前要求内。

## 8. 损坏数据与显示

正常兼容链不应制造缺记录物品。缺记录、枪型不匹配、非法数值和混合格式是数据损坏，应与正常升级区分。

- 在布局已经确认且型号可靠时，保留对应枪名和图标，提示“枪械记录待恢复”，禁止猜测弹量和耐久后直接放行。
- 无法可靠确认型号时，不伪装成另一把枪；显示明确的数据异常提示和恢复入口/说明，原文保留。
- 不凭缺失记录创建满弹满耐久枪，不静默删除或改写未知物品，不通过清空注册表消除错误。
- 格式级别无法理解时按上一节拒绝正常加载；局部损坏若允许继续，必须先证明保存能原样保留异常数据，且无误用/改写路径。不能用局部容错绕开格式保护。
- 显示改进不等于数据恢复；恢复来源应是可信备份或可验证记录，不能承诺恢复已经丢失的原枪信息。

## 9. 基准存档与发布检查

保留不可覆盖的正式 0.28.2、0.37.0 基准存档，以及以后每种正式数据格式的样例。每次测试复制到独立目录，禁止覆盖原件。记录来源包版本、提交/哈希、格式、依赖模组和预期枪械状态；样例进入两端可获取的正式测试资源目录，不依赖仅本机的临时文件。

| 检查组 | 最低证据 |
| --- | --- |
| 全枪型状态 | 满耐久、部分磨损、损坏；满弹、空弹、部分弹量；消音器两状态 |
| 实例独立 | 同型不同状态两把枪、创造复制隔离，两把电击枪分别充能 |
| 持有位置 | 生存/创造背包与快捷栏、原版箱、Stash、掉落物、投射物、移动方块；其他已支持容器及补偿记录 |
| 保存回归 | 源档升级、保存退出、重进，再保存重进；枪型、数量、引用和状态保持正确 |
| 跳版本与重试 | 跨过中间版本逐级转换、重复加载不重复补满/退款，保存前退出可重试 |
| 容量和损坏 | ID 表满、缺记录、坏记录、未知型号、混合标记不发生部分转换或资源损失 |
| 未来格式 | 未知布局/schema 拒绝加载及误保存，原文件/版本信息保持不变 |
| 故障注入 | 备份失败、转换中断、写盘失败；有效备份保留，失败不报成功 |
| 参数升级 | 耐久比例、弹匣超额、充能规则及无状态模板按该版约定处理一次 |

纯解码断言不足以证明兼容。自动检查应覆盖真实 XML/记录序列化与重读，并对失败前后的源文件做一致性检查；容器交互、手机 UI 和引擎真实写盘失败需单独给实机证据。离线通过与实机验收分开报告。

每次涉及枪械数据或其语义的发布，交付说明必须给出：源/目标格式、是否需要迁移、每个变化字段的处理规则、覆盖的持有位置、备份和失败行为、测试证据及剩余限制。没有变化则明确说明布局/schema 不变，并执行与改动风险匹配的存读档回归，不要求纯文档或无关资源改动跑全套迁移测试。

| 项目 | 截至 0.37.0 的状态 |

| 未来布局/schema 拒绝加载及保存 | 待补齐与验证，优先处理；特别核查显式未知戳被重新保存成旧戳的路径 |

## 11. Agent 执行入口

Codex 和 VPS Claude 在修改枪型编号、`GunSpec` 编解码、注册表/schema、保存加载、充能/耐久参数或关联库存事务前，必须阅读本文。先列出格式和旧状态影响，再实施与验证；不得沿用旧规划“新建世界即可”的历史豁免。

仓库 `AGENTS.md` 和 `CLAUDE.md` 保存简明硬要求并链接本文，本文作为完整规则的单一维护入口。0.28.2 已实现行为仍参考 [实施与验证记录](official-0282-compatibility-0370.md)，M4 事务和流转继续参考 [M4 专项方案](vps-m4-durability-plan-2026-09-08.md)。
