## 1. 目标

- CS 的联机功能（重点是死亡竞赛附加包）在 1.9.5.1_MP 上正常；
- 1.9.3.2_MP 照常能用，一套包同时支持两个联机引擎；
- 单机引擎行为不变。

两版联机层的差别（源码对比）：
- Multiplayer 只改了两处：`PlayerCreatePacket`（`From == null` / `PlayerIndex >= 0` 判空）、`NetworkModLoader`（房主不再在非客户端状态下排队 `PlayerBodyUpdatePacket`）。CS 用到的 35 个传输契约成员都没变。
- CompatNet 从 45 个文件减到 15 个：去掉 `CommandCompatNet`（就是 1.9.3.2_MP 冻结问题的来源）以及 Gunsmod/Elytron/Enchantment/IE2/MCHszr/ScopedUpdateGuard/Subnautica 适配器，新增 SiyahAkrep/neorxna，协议号 3；Compat23 被删。
- 上游 TestAutomation 未打补丁，测试时照旧只在隔离副本里改成只听本机。

构建坑：干净树第一次构建 `Survivalcraft.Windows` 会报 MSB3030（CompatNet 的 .scmod 先被复制、后才打包）。`m0.py mpsrc` 先放一个空 zip 占位，构建后检查两个内置模组里确实有程序集。

## 3. 基线（已交付的 1.5.2，未改动）

- ABI：1.5.2 的全部 CS 程序集在 1.9.5.1_MP 上成员绑定 0 问题（与 1.9.3.2_MP 相同；两边都只有资源程序集 `ScCsgoResources`/`ScCsgoResourceCodec` 不在引擎构建里，属预期）。
- 实机死亡竞赛（全量 + 死亡竞赛包，1.9.5.1_MP）：15/15 通过，日志无错误；联机适配器正常挂上，地形补发开着，平台记为“未验证”。
- **发现的问题**：1.9.5.1_MP 已删掉 `CommandCompatNet`，CS 的冻结修正包按协议 2 检查不匹配而不加载，于是玩家进联机世界会看到
  “CS 联机：平台冻结修正未能启用（…）”。这条提示是误报：要修的东西上游已经删了，不需要修。

## 4. 改动

- `src/ScCsgoKnives/Net/ScNet.cs`：CompatNet 里如果没有 `CommandCompatNetAdapter`/`CommandCompatNetRuntime`，记为 `upstream fixed: this CompatNet has no CommandCompatNet adapter …`，不再尝试加载冻结修正包；`PlayerNotice()` 对 `upstream fixed` 本来就不提示。1.9.3.2_MP 的判断路径不变。
- `tools/MpM0/m0.py`：`M0_MP=1932|1951` 选引擎；`mpsrc` 构建 1.9.5.1_MP；`prepare`/`tapatch`/`abi` 按引擎分目录和结果名；记录里的路径不再假设都在 `.tmp/mp-m0-20260929` 下。
- `tools/MpM0/mp_deathmatch.py`：新增房主、客户端各一项检查“CompatNet 判断符合当前引擎且没有平台提示”（1.9.3.2_MP 要 `command gate: installed`，1.9.5.1_MP 要 `upstream fixed`）。
- `tools/completion_140.py` / `tools/deathmatch_140.py`：发布流水线的 netloop / dmloop / dmabi 同时对 1.9.5.1_MP 引用集跑一遍。

提交：`3def090`、`fd224c8`、`d317a68`、`dd3e4b8`，本文档单独一次提交。
