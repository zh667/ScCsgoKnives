## 1. 启动固定资源开销

实际1.9.3.1 `Game.ModEntity.CombineContent`遍历全部Assets成员，逐个ExtractFile到MemoryStream，并由ContentManager.Resources保存。贴图“按需解码”不等于压缩图片文件本身按需从磁盘读取。没有发现本模组绕过该入口的惰性资源加载器。

|---|---:|---:|
| 全量 | 502.3 | 593.5 |
| 轻量 | 34.0 | 48.9 |
| 探员 | 36.7 | 45.1 |

全量Assets为622,373,146字节：贴图395,678,663，模型163,433,121，动画44,530,580，音频18,256,934等。轻量+探员合计Assets约94.0MiB。表中是加载路径保留的资源有效载荷量，不是进程PSS/RSS：MemoryStream容量、程序集、运行时对象、临时分配、GPU及游戏/其他mod还需另计；手机具体构建应核验相同加载路径。内层SCZSTD资源的这一列是包内编码流大小，不是再次展开后的大小。

因此只优化“常用枪缓存”无法消除全量包启动阶段近600MiB的资源载荷；只改变外层ZIP压缩率也不能减少解ZIP后的驻留内容。

## 2. 解码图片与GPU纹理会叠加

实际1.9.3.1 `Texture2DReader.Get`经`ContentManager.Get<Image>`解码，`Texture2D.Load(Image)`创建Rgba8888纹理且`Tag=image`；ContentManager还缓存Image和Texture2D。已解码图片与GPU像素可同时保留，不能上传后随意Dispose图片：设备恢复/共享引用需要正确处理。

一个1024² RGBA图片约4MiB；同尺寸颜色、法线、ORM三张合计约12MiB CPU像素，GPU基础像素另约12MiB（不含编码流、几何、驱动开销）。512²是其1/4，256²是1/16。PNG/WebP文件很小并不保证解码后很小。

全量716张纹理中442张1024²、12张2048²；若把所有图片各解码一份，总RGBA约2077.4MiB。轻量659张约259.4MiB、探员57张约51.6MiB。这些是**全部图片展开的理论总量，不是同时加载量、真实峰值或精确上限**，不能对玩家宣称“必占2GB/4GB”。当前UI枪械图标走单独slot图，不应误称打开创造列表就加载所有高清枪皮。

`ScGunVisualMaterial.s_cache`与`KnifePbrRenderer`的颜色/PBR贴图字典没有字节预算；已加载贴图由原生ContentManager持有。核心退出世界清自己的颜色字典不等于释放引擎Image/Texture2D；PBR字典也不在该清理路径中。换看更多皮肤/模型会增加保留资源，有明确增长压力，但目前没有实测证明无限泄漏。

## 3. 以前的“缓存”做了什么

- CT/T `.scanim`：预先烘焙原生动画采样，跳过昂贵glTF转换，主要解决召唤/打开外观列表卡顿。全量CT/T二进制共44,521,587字节；加载后还产生通道、Quaternion/Vector3数组等，挂在共享Model上，不是零内存。
- 武器`.scmesh`与NPC GPU缓冲：避免逐帧重复变换/复制顶点，降低累计临时分配和GC。CPU源数据与GPU缓冲仍需驻留；GPU缓冲退出世界有Dispose。历史“累计分配约3GB”不是同一时刻驻留3GB。
- `ScResourceCache`：动画、刚体武器、蒙皮武器各40条；NPC几何80条；第三人称/掉落各12条并允许最近2秒使用资源超过软上限。它按条目而非字节控制，不是全局内存预算；清引用也不保证没有引擎/其他对象继续持有。
- `ScRigidBuffers`：8组几何GPU缓存，淘汰和退出世界会Dispose，属于已有有效限制。
- `ScTexturePreparation`：2个解码任务、最多8个待消费请求、64MiB估计RGBA预算；预算在结果转交ContentManager后释放，**不是已加载全部纹理的64MiB上限**。原始编码字节、解析器临时内存等也不全在该预算内。

所以缓存并非做错或应全部删除：它以保留可复用数据换低延迟；当前欠缺的是对启动资源、CPU像素、GPU纹理、动画/几何总量的统一核算与合理回收。盲目缩到很小会恢复切枪卡顿。

## 4. 建议优先级（待实施，不在本次修改）

1. 优先评估自有资源的按需载入/内层无损压缩，减少全量启动时所有Assets原始流驻留；必须适配1.9.3.1资源注册时序、第三方读取与设备恢复，不修改第三方引擎。不要只重新压ZIP，也不要无证据删掉仍被引用的资源或降低Full画质。
2. 贴图建立按字节计量、使用中固定、闲置可回收的所有权机制；统一颜色/PBR/原生缓存别名，避免单独删除字典却仍被其他对象引用，或提前Dispose共享纹理。处理CPU图片、GPU纹理和恢复所需输入，不能以强制GC代替释放引用。
3. 动画/几何按实测字节和工作集预算，保留正在持有及邻近实际使用资源；复用已有缓存，避免重做全套或过小LRU导致频繁重解析。CT/T共享动画不要每个NPC复制。
4. 手机玩家现阶段优先轻量；需要探员则轻量+探员，不能再叠加全量。此建议是现有版本选择，不授权削减全量质量。

## 5. 最小测量方案

内存是用户肉眼难可靠验证的隐藏状态，后续优化需要自动采样，而非让用户“感觉一下”。先在1.9.3.1隔离环境做同输入基线对照，再在实际Android同API构建上测一次：无CS / 轻量 / 轻量+探员 / 全量，其他mod、世界与视距固定。节点为主菜单、进入空测试世界、首把枪、轮换若干枪皮、首次CT/T、第二次重复同一组、退出世界、重进；记录进程PSS/托管堆、可取得的图形内存及自有缓存字节/条数，同时记录首用与重复切换帧耗时。

重复同一组后趋于平台与不断增长是不同问题；只看GC堆不能代表GPU/原生内存。记录引擎和包哈希。不要为此重跑烟雾/联机全矩阵；本次没有启动这些测量，也未安装手机或改玩家世界。
