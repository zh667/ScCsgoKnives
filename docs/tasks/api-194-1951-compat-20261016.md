## 已执行的检查

### 二进制契约（Windows 作业 `9d29cf58…`，工具 `.tmp/dev-temp/api195-compat/audit/`）

输入：候选 `als1` 的全量/轻量/探员包（内容与 main `8fcb56b` 的产品代码一致）＋ output 根目录 1.5.0 死亡竞赛包，共 10 个不同的 DLL；引擎为各版本 Windows 运行目录中的实际 DLL（1.9.3.1 为 `D:/下载/[Windows]SurvivalcraftAPI_1.9.3.1`）。

- 四个引擎上 10 个 DLL 的引擎类型/成员引用全部可解析；重写的虚方法/钩子没有一个失去基方法；没有未实现的抽象成员或接口成员。
- 反射访问的引擎内部字段 `ContentManager.Resources/Caches/syncObj`、`TerrainSerializer23.m_storage/m_lock` 在四个版本中都存在，类型不变。
- 相对 1.9.3.1，被继承的引擎类型只新增了虚方法，未删除：`ModLoader` 新钩子（1.9.4 两个、1.9.5 共 12 个）；1.9.5.1 `Block.GetDrawDemand` 与粒子系统 `MaxQuadDemand/QuadDemandTexture/GetBatchDemands`。
- 结果文件 `.tmp/dev-temp/api195-compat/binary-contract.json`。静态扫描看不到签名不变而行为改变的情况。

### 引擎源码对照（gitee 标签 `API_1.9.3.1` 与 `API_1.9.5.1`）

- `Block.GetDrawDemand` 默认按立方体估算，源码注释写明未重写时"实际走 mesh 时仅多备容量，无正确性问题"，只影响预扩容性能。我们按 1.9.3.1 编译，不能重写它。
- `IndexBuffer.SetData` 新增 16/32 位互转，同宽度直接上传。我们自建的两个索引缓冲（`ScRigidBuffers` int→32 位、`ScNpcWeaponRenderer` ushort→16 位或按顶点数选择）走直接上传路径；直接绘制引擎模型的代码只把引擎自己的索引缓冲交回引擎绘制，不读其格式。
- `DynamicArray`、`VertexBuffer` 无变化。
- 1.9.5.1 的粒子系统在加入/移除时按"贴图 + 粒子数"记账预扩容，要求两者在生命周期内不变。我们唯一的粒子系统 `ScHelmetSpark` 在加入前设好贴图、粒子数组固定；烟雾/枪口效果用自己的渲染，不走引擎粒子系统。
- 烟雾贴图上传用 `Texture2D.Load(Image)`（绕开 1.9.3.1 `Texture2D.SetData` 的缺陷），新引擎上同样成立。
