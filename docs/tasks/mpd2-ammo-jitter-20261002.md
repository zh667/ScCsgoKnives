## 2. 已证实的代码机制

源码入口：`src/ScCsgoKnives/World/SubsystemScGunBlockBehavior.cs` 的 UpdateGun / Fire / WillFire；`Net/ScNetGuns.cs` 的 PredictShot / ServerSettle / ApplyAck / ShownRounds。

1. 客户端与房主各自按自己的更新帧判断 `now >= state.NextShot`；普通射击后设 `NextShot = now + cycle`。每次等到下一帧再执行所多等的时间被计入下一发起点，两个更新频率或抖动不同的端会逐发累积节奏偏差。
2. 客户端先播放射击并增加预测数；显示弹量是“服务器镜像弹量 − 仍未结算的预测数”。这一阶段不修改权威枪记录。
3. 当前上行以扳机状态、按下事件和累计已显示数为主；服务器独立跑射击状态机。停火已到达而服务器尚未打出的预测，在 `WillFire=false` 时由 `ServerSettle` 标成 Skipped。
4. Skipped 随枪记录一起回到客户端，`ApplyAck` 清掉这一发预测；服务器原本没扣的那一发重新显示。确认层在纠正先前多显示的射击，不是执行一次加弹事务。

mpd2 已修正旧的 ACK/Hit 编号冲突及记录/确认分离。这一发回升属于仍保留的预测与权威射击节奏差异。不能把它概括成“房主帧率低于武器射速所需”：约 50 FPS 仍能复现，而 AK 射速远低于 50 发/秒；问题是时间取整和从实际帧重设下一发起点。

## 4. VPS 下一轮建议与可反证检查

建议只修射击节奏与输入/预测对应关系，保留已经修好的消息注册、记录与确认同消息、权威换弹、实例身份和既有行为。以下是实施建议，本轮没有实施授权或自动向 VPS 发送消息。

- 优先消除 `NextShot=now+cycle` 的逐发误差，采用稳定的射击时间轴并保留跨帧余量；任何追赶都必须有界。同时检查停火消息在同一服务器帧批量到达时，停火前已合法产生的射击如何对应权威事务。只改一个赋值不能证明整个问题消失。
- 如果现有扳机状态＋累计计数无法完整表达这段历史，再评估加入逐发请求/时间或由确认节奏限制预测；无需先建设另一套通用网络系统。服务器仍验证射速、弹量、玩家状态、枪选择和租期，不能相信客户端报的发数直接补射。
- 验证应记录每发显示/请求/服务器执行或拒绝的对应关系、Fired/Skipped、实际帧时间与确认接收时间。HUD 单调或最终弹量正确都不足以证明每个显示出来的合法射击实际造成过相应权威结算。
- 扩展正式 GunLoop：加入 100/50 与 60/50 等不整齐节奏、帧耗时波动、输入在帧内成批到达、不同按下/松开相位、固定延迟和有序抖动。正常短连射不能依靠 Skipped 抵消多预演的一发；非法/取消的预测仍允许正确回滚。
- 回归自动/手动换弹、点射、连射、FAMAS/Glock 三连发、R8 蓄击、菜单与切枪、过期输入和断连。稳定射击时间轴可能影响实际射速，须在 API1.9.3.1 单机与联机分别验证受影响行为，不把“射速更快了”自动当正确。
- 不用 HUD 钳制、假扣弹、额外补伤害、延长预测超时或篡改权威记录遮住变化。网络延迟不能消除，但本次已证明回跳并不需要传输延迟。

验收仍由用户完成实际主客方向测试。本次视频的精确触发条件需要新增的有界逐发诊断；现有日志没有这些字段。当前最有证据支持的解释是“停火后被拒绝的一发预测回滚”，帧调度差异与链路抖动均是已复现的触发因素，不能单独断言真实视频只由其中一个造成。
