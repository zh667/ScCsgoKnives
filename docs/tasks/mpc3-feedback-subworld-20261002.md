## 3. P0：OpShotAck 与 OpHit 同为42

源码与实际 DLL 一致：

- `ScNetGuns.cs:80` 新增 `OpShotAck=42`；格式是两个 Int32（selection、累计 fired）。
- `ScNetFeedback.cs:10` 原有 `OpHit=42`；格式是 Byte outcome、String target、String weapon、Float distance。
- `ScCsgoKnivesModLoader.__ModInitialize` 顺序为 Guns.Register 后 Feedback.Register。
- `ScNet.OnClient` 用字典赋值，重复编号静默覆盖。因此最终42的处理器为 `ScNetFeedback.ReceiveHit`，射击确认收不到。

实际安装 DLL 的离线复现：按正式顺序注册两组处理器，发 selection=7/fired=2 的8字节 ACK，经真正的接收字典后 HitsReceived增加；按命中格式读出 outcome=7、两个空串和极小distance，还剩未读字节。`ScCombatFeedback.Record` 只拒绝<=0，其他非2/3的正值都画白杠。因此没有生物命中也会出现白色提示。selection低字节为2/3时还存在假击杀/爆头展示风险；这是显示路径，不等于真正发放击杀成长。

同一探针设置服务器弹量2、本地两发pending：显示0；实际ACK被错误路由后仍0；让pending过期，显示回2。**白杠与弹药跳变共享一个确定根因**，不是延迟大就必然如此。

已有 `tools/NetLoopCheck/StateLoop.cs:137` 注册了 Mirror/Guns/Grenades/C4，漏了 Feedback，故没有覆盖生产注册冲突。此前83/83属于那套夹具，不应据此否认本次实机失败；新集成门禁必须使用实际全部注册集合。

修复要求：为ACK分配经过全模块核验的唯一编号；按方向分别校验全表，禁止不同handler静默覆盖；合法重复初始化应显式清理/幂等，不在正常二次初始化无条件崩溃。校验消息全长、合法outcome和字段边界，畸形ACK绝不能变成命中。需要协议/能力身份更新，混用旧新候选明确拒绝。

## 4. 首次换弹0→2，以及修完编号后还必须验证的时序

第一层是已复现的显示：权威剩2被未确认预测减成0，1秒超时后回到2。
第二层是代码支持的因果解释：客户端 `UpdateGun` 使用 ShownRounds 判断空弹并自动 StartReload；服务器使用真实 rounds。客户端预测为0、服务器仍2时，两边可能各自进入不同状态。自动换弹没有因为本地 StartReload 就发送独立的换弹请求，现有 SendInput发的是按键/扳机；若玩家已经松扳机且服务器没有空弹，它不会凭本地动画完成装弹。

因此首段“播了完整换弹但仍2”、第二次打完真实剩2后才装到30，与当前代码吻合。日志没逐发、逐次reload/输入trace，不能断言首次一定是自动换弹而非其他取消路径。后续用实际完整枪状态机＋输入事件序列确认，不能用一个复制条件的小测试替代。

编号修复后还需验证：

1. 记录更新与ACK虽同可靠有序通道，却是独立消息；不能未经帧调度验证就假定任一可观察帧都同时应用两者。必要时把记录revision/ACK水位关联或同包应用。
2. ACK累计 fired 与pending队列不具逐发身份。超时移除旧预测后，迟到累计ACK可能错误抵掉刚入队的新预测；需要区分“确认旧发”和“确认新发”，不能只按数量从队头减。
3. reload要有服务器接受/拒绝/完成与对应选择/动作序号；本地动画不构成装弹成功。自动换弹与按键换弹均覆盖，取消/换枪/断流明确处理。

最小验收：对空海面射击0次命中提示；正常躯干/头/击杀仍正确；长按、点射、预测超时后再开枪、首次自动/手动换弹、记录与ACK跨帧到达；观察HUD、权威记录、pending、accepted reload四者，不靠“看起来平滑”掩盖服务器纠正。

## 5. 匪徒新行为与用户澄清

确定需求：自然生成和手动召唤的匪默认中立；一名匪受到有效攻击，附近所有匪攻击同一个攻击者。附近不限同Squad或同Source；不能一受击就全地图或所有无关玩家都敌对。用户强调的群体同目标行为必须保留。

当前代码：Enemy.Update会扫描玩家和伙伴主动设TargetBody；HearNoise启动搜索但不直接给攻击目标；ProcessAttackment直接Alert受击者。伙伴Hostile目前把所有ComponentTacticalEnemy判为敌人。没有找到CS源码中明确的“受击者广播给全部附近匪”调用；旧现场附近匪同时参与，可能有各自主动索敌/声音搜索及引擎/其他行为共同作用，未做运行时追踪，不能给用户观察定性为不存在。

设计：先确认既有群体响应可复用部分；中立时关闭未经挑衅的主动攻击，保留观察、走动、受惊/避险。服务端在有效受击事件提取同一攻击者和受击位置，发布一次局部挑衅事件给附近活匪；不要递归从每个被通知者继续无限传播。攻击者无有效实体（环境掉血）不猜最近玩家。玩家/伙伴/第三方生物作为攻击者都按同一规则；误伤盟友过滤、防同阵营互殴保留。

“附近”未指定距离：建议先复用现有32格量级作为候选参数，在实施决定中明示，不说是用户指定。广播得到共同目标不等于可隔墙开枪，仍用现有视线、烟雾和寻路规则。脱战延续现有有界遗忘/距离规则，除非用户进一步要求永久仇恨。召唤暖机结束不得恢复自动敌对；伙伴不主动攻击未挑衅的中立匪，但仍可保护主人或协助主人已发起的战斗。

用例：野生/召唤/混合不同小队；玩家只是靠近或在旁边开空枪不挑衅；有效攻击后附近全部锁同一实体，远处不响应；受击者当场死亡也触发一次；墙/烟挡射击不消除挑衅；A攻击时无关B不被随机替换成目标；客户端不自行改变仇恨；已存在匪/加载旧存档不会因Source缺省继续主动敌对。

## 6. 子世界：已经发生编号冲突，不只是“表分开”

Game (3).log：

- 694行：远古子世界 gun registry=1，Next=4；966行：主世界records=7，Next=8；1209行再次进入远古仍1/4。
- 540/543行、1056/1059行：子世界 `CreativeInventory/Slot2 / #1：物品为法玛斯，记录为M4A4`；另 `Slot6 / #3：记录缺失或已隔离`。
- 823/825行：回主世界 `Slot9 / #1：物品为M4A4，记录为法玛斯`。
- 819和1052行是双向切换，1049和1301行旅行者数据恢复；1296行 unusable gun data71，编码为record1/variant7。没有 `[GUN_TRAVEL] imported` 成功记录。

结论：不同世界分表本身正常；出错在携带的局部数字ID没有与原枪完整记录/稳定来源身份一起重映射。错误型号被校验拒绝后走物品图标绘制，因此像纸条。不能只修3D显示就让枪安全互通。

更隐蔽的同型号碰撞也要防：两个世界都有ID1且都是同型枪时，型号校验可能通过，却读到另一把枪的弹药、皮肤、耐久和成长。不能把“不再出纸片”当作迁移成功。

现有CS已有 `ScGunTravel`：保存钩子给玩家XML附带ScGunTravel快照；ProjectXmlLoad阶段导入并根据稳定身份重映射，不合并两个世界整张表。V3支持任意目标路径，并非只有旧Tartareosity白名单。Prepare在没有携带快照时直接返回null。实际mpc3 DLL＋合成XML复现：源ID1、目标已用ID1；携带快照完整则导入为ID2，移除快照则无迁移计划。此测试证明机制边界，不能证明反馈者包就是mpc3或远古代码具体在哪丢数据。

未取得反馈者实际CS包、远古0.41.15包/源码及其旅行前后脱敏玩家数据，Windows和检查过的VPS项目目录未找到相应远古源码。当前仍需区分：只复制白名单玩家组件而丢ScGunTravel；直接保存实体未走ProjectXmlSaved；玩家在ProjectXmlLoad后才恢复；携带了旧/错误Source快照。先接入实际提供方生命周期，不瞎加目录名判断。

处理方向：

1. 源端在传送提交前读取当前携带枪完整记录和稳定世界/枪身份，确认快照对应实际slot、count和revision；不能从目标表反推。
2. 旅行者数据结构携带快照，目标端在让枪可用前校验并原子导入记录/重映射槽位。若提供方是加载后恢复，增加明确生命周期适配；只在ProjectXmlLoad查一次不足。
3. 再往返映射回同一稳定身份，保存子世界内发生的消耗/皮肤/成长/充能变更；不每次生成全新枪，不覆盖目标世界别处持有的同身份物品。
4. 当前主世界CountAndGrow、子世界Unset不等于必冲突；已有逻辑允许Unset采纳。双方明确且不一致的成长规则需要保留现有拒绝/明确方案，不能静默改枪属性。
5. 已经串号/缺记录的枪不能补满或随意绑定同型记录。恢复必须有原世界记录＋来源证明，只读分析后提出具体恢复方案；不在玩家原世界自动尝试。

目标覆盖：已有/新建子世界、A→B→A、B原生枪→A→B、同号不同型/同型、两个玩家、目标已有另一把实体、加载后恢复、重复提交、失败/回滚、保存重启；其他提供方按实际接口确认，不宣称所有子世界天然兼容。
