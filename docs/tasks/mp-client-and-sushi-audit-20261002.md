## 3. 共同缺口：枪记录同步与槽位身份同步脱节

调用链：

1. 服务器 `ScGunMutation.Commit` 给新枪、皮肤模板或真实复制品分配编号，更新记录及槽位（`ScGunMutation.cs:129–174`）。
2. 创造槽位走 `ScGunInventoryJournal.ReplaceCreative`（`ScGunRecovery.cs:186`），调用引擎 `ComponentCreativeInventory.AddSlotItems`。
3. 实际平台 DLL 该方法只写 `m_slots[slotIndex]`，不触发库存网络变更钩子。我们的 `ScInventoryTransaction.Changed` 也只加自己的内存版本号，未发库存同步。
4. `ScNetMirror` 广播的是枪表行，不包含“某个库存的某一格已经从旧 value 换成新 value”。服务器和客户端可以有同一份枪表，却持有不同的枪编号。
5. 实际平台 `DragDropItemPacket.Handle` 完成操作后会发整份 `InventorySyncPacket`。以后再拖入/拖动物品时，旧的改号才可能顺带同步过去。

这是当前模组依赖创造库存自动联网通知、但平台实际没有该通知的集成缺陷。我们应在成功事务边界补充明确的槽位/身份同步，不能通过每帧分配新 ID、客户端补造记录或放弃服务器权威来处理。

## 4. 下包声：明确的房主播放条件错误

`SubsystemScC4.Sound:101`（已对照 mpb DLL）：仅在 `shownBy == null || ScNet.IsLocal(shownBy)` 时本机播放。客户端玩家在服务器不是 local，因此房主不播放；接着 `ScNetGrenades.Sound` 只向其他客户端广播，并排除已经自己播放的下包者。这不会回送给房主自己。
房主下包时 local=true，本机播放并广播，因此方向恰好不对称。
影响不止按键音，同样通过 shownBy 参数调用的 initiate 和放置完成声也应覆盖。修复应区分“拥有者客户端已预测播放”和“房主是旁观听者”，保证每个应听到的人恰好一次。
本轮两端均轻量包，不用旧全量 Ogg 立体声问题解释这个方向性错误。没有双端音轨，依据是用户报告与确定的代码条件。

## 5. 其他相关隐患

1. **改号后其他属性也会错读**：消音器、充能、击杀计数、等级、耐久、装配台状态均挂在记录上。补皮肤刷新或 HUD 文案不足以修复根因；复制隔离、回收补偿、维修后也需测试身份与记录一致。
2. **预测状态未按世界隔离**：`ScNetGuns.s_predictions` 以整数 ID 为键，无世界/会话，退出清理没有清该表。实际 DLL 的离线探针构造“上个世界 ID7 尚有预测，新世界 ID7=20”，超时会写回旧 5。只证明该状态切换风险，不声称用户本次已触发；真实退出回调时序还需专门检查。
3. **枪输入不携带所针对的槽位/枪 ID/选择序号**：`SendInput/ReceiveInput` 只发标志、缩放、射线。快速切枪/拖动与输入分开发送时，服务器可能对它当时的活动枪执行旧输入。需要带期望身份并核对，不靠视觉动画判断。
4. **输入无过期闸门**：`ScRemoteGunInput.ReceivedAt` 只有赋值，没有读取。已记录按住开火、后续释放包停滞但连接尚未断开时，服务器仍可能继续使用旧按住状态。属于代码风险，未在本次视频复现；应有有界租期，并保留短按计数语义。
5. **已有运行警告**：房主多次“Gun hit pose unavailable → body-only fallback”，以及 4 个不同区块在 6 次修补后仍不一致（-7,3 / -7,4 / -12,15 / -3,7）。这两项分别提示精细命中判定退化和地形一致性问题；未定位独立根因，不把它们直接归咎于记录表。

## 6. 耐久/记录设计判断

“物品带实例编号，世界表保存弹药、耐久、皮肤、成长”本身合理；每发只更新原记录，并非每发新分配。移动同一把枪应保留编号，真正复制才分配新编号。不要为本次联机故障推翻历史 ID 或把所有数据挤回有限的方块位段。

薄弱处是跨系统契约：

- 记录事务只保证本进程，尚未把库存 value、记录 revision、网络确认组成同一次权威变更。
- 第三方把枪当普通整数物品搬运；CS 的私有 revision 不会自动观察第三方写入。现有 value/库存/记录检查能挡住部分过期事务，但不能宣称覆盖所有直接写槽位和变更后又恢复原 value 的情况。
- 世界级整数 ID 需要会话隔离和稳定库存标识配合；客户端预测不应直接成为所有显示路径共享的“权威镜像值”。
- 动态库存、共享代理、离线存储需要明确适配；基于扫描的重复隔离适合兜底，不能代替完整的移动/复制事件语义。
- 编号不回收保护了旧物品引用，但有效实例容量有限（66,558）。误把代理或转运中间状态当复制品，会浪费编号；不能靠盲目回收弥补。已存在旧包兼容及防损坏保护，应保留。

建议先补统一事务提交后的库存与记录同步、客户端确认/重取及会话清理，再提供物品“独立实例/禁止堆叠/状态读取”契约和第三方库存适配。暂不建议重做存档格式或改耐久数值。

### 7.1 已证实的条件冲突：堆叠

CS `ScNoDurabilityBlock` 对原版接口 Durability=-1，真实耐久在枪表。枪 CSV 配置 MaxStacking=1、IsPlaceable=false。
玲兰 `SushiUtils.GetNewMaxStacking:1101` 在“调整堆叠＋无耐久非放置物堆叠”开启且小堆叠上限大于 1 时，恰好把 CS 枪包括进去。`ApplyMaxStackingTweaks` 改全局 block.MaxStacking，普通玲兰箱/同步箱也会重新调用该规则。
实际 DLL 离线结果：选项关闭 1，开启并选 4 后变 4。未修改用户设置；默认这些开关为 false。
CS `ScInventoryTransaction.IsWeaponSlot` 对非创造库存要求 count==1，因此堆成一格后可能无法射击/维修/事务；同 ID 的多份枪在同一格时，持有者扫描按槽位计，不能把数量当成多个独立实例。不同 ID 不会仅因同皮肤自动合并，不能夸大成所有皮肤枪必串号。

### 7.2 个人箱：别名去重已保护，联机玩家归属仍有问题

`ComponentSushiPersonBox` 所有操作都转发到 `SubsystemSushiTotal.ComponentMiner.Inventory`；`ShortInventoryItemMonitor` 初始化时取 `ComponentPlayers[0]` 并缓存。一个全局 Miner 不能表达不同联网玩家各自打开的个人背包。
我们当前 `ScInventoryIdentity.Storage` 能把这些代理映射到真实库存。实际 DLL 离线验证“真实背包＋6 个个人箱→1 个 holder”，此项保护有效，不应删除重做。
但它只解决重复计数，不能把错误的玩家绑定变正确。多人时必须由服务器根据请求连接确定玩家及真实库存；现有平台源码未找到对这个全局个人箱归属的专门修正。未来联机包可能改变，需按其实际实现核验。

### 7.3 同步箱：共享存储、网络桥、持久频道身份

`ComponentSushiSyncBox` 是代理；真正槽位在 `SubsystemSushiSyncBox.SushiSyncInventories[channel]` 中，`SushiSyncInventory` 不是实体组件。我们已有共享频道去重、无箱仍扫描频道库存、事务固定实际存储，以及回滚目的地检查。
当前平台源码另有 `SushiToolCompatNetRuntime`，负责频道快照、控件请求和机器控制，依赖 CompatNet。**CS 自己改用包 197，只解决 CS，不会自动让玲兰通道也在缺 CompatNet 的安卓平台可用。** 不能把当前 CS 安卓验收外推到玲兰。
频道数字可删除后重用，没有持久 UUID。我们 `ScSushiInventory.Resolve` 在重载后对旧补偿故意不猜目的地，会保留未完成补偿并可能封住同号频道；这是防误退物的保守边界，不等于无人干预即可恢复。长期方案应提供频道持久身份/代次。

### 7.4 新发现：同步箱删除中间频道后保存异常

实际 `RemoveChannel` 只删除字典键，不重编号；但 `Save` 按 0..Count-1 取 `SushiSyncInventories[j]`，假定键连续。
已用真实 SushiTool DLL 在隔离内存中创建频道 0/1/2，调用实际 RemoveChannel(1)，再实际 Save：剩 0/2，抛 `KeyNotFoundException: key '1'`。没有触碰玩家世界。
补充可达性边界：反编译目录中没有找到当前 UI 对 RemoveChannel 的调用。这是已复现的频道接口/稀疏数据保存缺陷，不能说用户现在点击某个现成按钮就必定触发；未来适配新增删频道或接收稀疏频道快照时尤其要避免引入该状态。
这是玲兰自身的持久化缺陷，单机也可触发，与 CS 枪表无关。要修保存/加载按真实键并保持引用身份，不能为了保存成功把频道随意重编号。是否导致整次世界保存中止取决于引擎异常处理，未现场触发。

### 7.5 整理、一键存取、自动补位、死亡保物

- 辅助包 `SushiInventoryControlWidget.Update` 直接调用 `SushiUtils.InventoryResort/TransportItems/AverageSet…`；原包无服务器请求语义。搬运保持完整 value，整理比较完整 value，**没有证据表明它会仅按同名把不同记录号直接写成同一号**。
- 但部分转运先加目标再删来源，批量整理分多次移除/重加；必须有服务器事务边界和变更通知。单线程同步调用中间态不一定被扫描，不应断言每次必误判；回调、网络分步复制和失败恢复仍需覆盖。
- `TryFillActiveItem` 自动补位会根据物品规则搬动/切换活动槽，且把自定义耐久枪识别成原版无耐久物品；与我们的换弹、连发、下包选择状态需协调。
- 死亡保物捕获/恢复 value+count，没有 CS 枪记录快照。物品编号不回收使已有引用能保留，但服务器重生、客户端状态、重复副本和待处理射击/换弹仍须一起验证。没有证据证明该功能一定丢枪，不应禁用代替适配。

### 7.6 机器/吸物箱/战斗输入

- 普通箱、挖掘机、建造机等继承 ComponentInventoryBase，已有 holder 扫描能看到其库存；投递时通常保留完整 value。吸物逻辑还要同步 worldItem.ToRemove / Count 和目标库存，防止客户端只删掉落物或只添库存。
- 平台源码对 SushiTool 有机器更新屏蔽与部分请求桥，但安卓缺该桥时不能保证机器只在服务器运行；联网修复不是我们只发枪表即可覆盖。
- 已检查辅助/科技的 Dig/Aim/Hit 钩子：有专用工具/玲兰剑条件，未发现无条件接管全部 CS 枪射速的证据。不能因为都叫武器就判定冲突。
