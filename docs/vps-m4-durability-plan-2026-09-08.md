## 1. 唯一目标与边界

交付标准：同一把枪在同版本的新世界中，无论换格、换玩家、入箱、丢弃拾取、死亡掉落、开箱获得还是保存重进，其型号、弹量、消音器、精确耐久和电击枪充能状态保持正确；复制出的另一把枪独立；失败的操作不损失物品、不增加弹量、不恢复耐久、不产生有效射击。

仅推进 M4。M0 的必要存储验证并入本专项；M1、M1b、M2/F07、M3、M5、独立开镜/检视及这些批次的专项实机验收均 BLOCKED，暂停时间见上。M4 允许修改共用接口的调用方以恢复原行为，不新增第三人称动作、烟雾功能、头区适配或战斗平衡。解除暂停须用户明确决定。

原先不实现任何迁移；2026-09-08 后续授权新增明确来源的 0.28.2 正式世界备份迁移，旧枪满耐久，见顶部兼容方案。其他历史格式/内部测试世界仍不猜测转换，不恢复已经变型号的枪、不回收 ID。拒用和防误写保护仍适用于不支持的来源。

## 3. 状态模型与不变量

保留 `GunSpec` 的纯型号表和纯位编码/解码。推荐由 `ScGunRegistry` 或新的世界级服务返回只读 `GunSnapshot`，通过事务写入，不把可任意修改的记录对象交给调用方。

记录至少包括：`Id`（表键）、`Variant`、`Rounds`、`SilencerOff`、`Durability`、`MaxDurability`、`Revision`、电击枪 `RechargeReadyAt` 或等价的世界游戏时间状态。普通枪的充能字段必须明确无效。满耐久在新枪实例创建时取确定配置；界面不自行猜测满值。记录结构若变化，增加独立记录 schema 版本，区分 item 位布局版本与记录 schema；本轮允许新建世界，不需要迁移旧 schema。

必须满足：

1. 型号在全部 35 枪明确注册；item 型号与 record 型号一致。未知型号、缺记录、schema 不认识、字段越界返回不可用，不默认满弹/满耐久，不自动重建。
2. `0 <= Rounds <= Magazine`；`0 <= Durability <= MaxDurability`；充能时间有限且语义有效。坏记录保留原始数据并隔离，不能覆盖另一把枪或静默补满。
3. 一件可变枪只对应一个已确认的有效持有实例。普通移动保留身份，复制分配新身份。跨世界粘贴既有实例值必须拒绝或通过显式“创建新枪”入口，不能碰巧绑定目的世界同 ID。
4. 查询、绘制、HUD、描述、列表刷新、报价不分配 ID、不改变记录。每个成功的可变操作增加修订号；单纯显示不增加。
5. 已分配 ID 不复用，不回绕，不把最大值当可用记录。保留未来 Next 水位；失败保存/坏记录处理不得让水位倒退覆盖曾使用 ID。
6. 世界上下文明确传入业务服务。若暂保留 `ScGunRegistry.Current` 兼容读取，Load/Dispose 必须严格绑定当前世界，测试切换和切世界不能读到前一世界状态；事务不得只依赖全局指针。

## 4. ID 分配与容量耗尽

无状态新枪模板可以继续延迟到首次真正修改时分配记录。复制模板仍是相互独立的新枪；两个模板值相同不代表同一实例。

所有操作先判断“已有有效记录”还是“需要新记录”。同一接口覆盖开火、弹匣换弹、逐发装填、消音器切换、复制、充能初始化、开箱创建以及任何未来入口。

推荐分配流程：Prepare 只验证额度并保留未发布的候选；Commit 在主线程再次验证后发布 ID。拒绝操作不占用可见记录，也不因鼠标连点耗尽表。已经实际发布或返回给外部的 ID 即使回滚也不得重用；若必须留下废弃记录/墓碑，记录原因并保持水位，不悄悄删除复用。

表满时：

- 新枪第一次射击、需要物化的换弹/装拆、实例复制必须失败，给可理解的限流提示；不能扣弹药、扣维修材料、改状态或触发有效射击。
- 已有记录的枪仍可射击、换弹、维修和保存，不能“一满表所有枪全锁”。
- 复制分配失败，拒绝复制或隔离尚未交付副本，原枪保持可用；不能退回到共用 ID。
- 不以扩大位宽或引入回收掩盖满表 bug。上限可以后续讨论，本轮验收必须实际填满测试。

## 5. 统一事务：先验证，再一次提交

建议接口（名字可调整）：`TryPrepareMutation` / `TryCommitMutation`，结果为明确的 `Success` 或失败原因，如 `MissingRecord`、`ForeignWorld`、`StateChanged`、`InsufficientMaterials`、`RegistryFull`、`DuplicateUnresolved`、`InventoryRejected`。不要用原 item value 充当失败标志，因为已有 ID 修改记录时 item value 本来就不变。

事务快照应捕获：世界标识、库存对象、格号/持有者、预期 item value 与数量、库存修改序号、record ID 与 Revision、旧记录副本、目标状态、材料逐槽扣除计划。维修须额外捕获工作台可用条件和报价，不允许点击时换用另一个库存对象。

执行顺序：

1. 只读预检：世界/记录可用、单件数量、持有者、库存和记录版本、操作条件、目标状态范围、必要 ID 额度、材料数量和目标槽容量。所有准备数据是快照。
2. 在权威游戏主线程提交，不在网络 await、绘制或 UI 刷新中修改；有重入回调时锁定相关库存/记录，并拒绝对同一目标再次提交。
3. 扣材料、必要时替换模板物品、发布新/更新记录作为一个事务。逐项检查引擎操作结果；`AddSlotItems` 无返回值时验证实际槽值/数量。已有 ID 优先原位改记录，不为每发射击删除再添加整把枪。
4. 任一步失败，精确回滚本事务已经执行的改动；不能只补回弹量而遗漏新 ID、耐久、充能或材料，也不能覆盖已提交的其他事务。失败返回明确原因。
5. 成功后再发一次库存/记录变更通知，安排后坐、弹丸/命中、音效、HUD。纯动画可以先播放，但失败时必须收尾，不能宣称射击成功或维修完成。

射击的有效伤害与扣弹/磨损须在同一权威提交路径中有“只执行一次”保证：先完成可失败的准备，成功提交后执行结算并标记该 shot；外部音效/绘制异常不能使同一 shot 再结算。霰弹按一次发射扣 1 耐久，不能按弹丸扣；三连发逐实际击发扣；最后 1 点耐久允许发出最后一枪，再变损坏。创造模式不磨损。

换弹保留现有结束时扣料、逐发霰弹逐次提交的语义。预检材料不足、取消、手动切槽、目标记录改变时不写表；因表满失败同样不得扣弹匣。满表已有枪可正常装填。

## 6. 复制、普通转移与持有者覆盖

优先在创造拿取/复制、开箱发奖、新造枪等真实产生新物品的入口创建独立身份；不能把所有 AddSlotItems、拾取或拿出箱子都当复制，否则普通流转会换 ID。

为实际 SCAPI/联动入口建立清单：玩家背包与快捷栏、创造可写格（区分无限目录）、原版箱子、Stash 等模组 IInventory、掉落物、死亡掉落、玩家交接、投射物/移动方块可能持有的物品、开箱待领取/奖励暂存、正在转移的事务。先核对真实 API，不能仅凭猜测的钩子名实现。未知持有者不得声称已覆盖。

补充持有者扫描用来发现历史/外部复制冲突，**不用于回收 ID**。在一致的游戏线程快照中扫描，排除转移事务中的短暂双持引用；同一库存对象重复被枚举应去重。玩家进入、读档后及复制/转移完成时触发必要检查。0.5 秒轮询只能作为兜底，冲突未处理前不允许射击、换弹或维修影响共享记录。

异常重复必须区分：

- 正常移动或事务暂存：保持原 ID，不克隆。
- 已知复制：保留原持有者，给新副本分配 ID；复制时取原枪当前状态快照，不补满。
- 来源不明的同时持有：在已确认的一致快照中选择并记录确定的保留者，对其他副本隔离/分配；额度不足时不能继续共用。不能只看“当前同一玩家有两把”。

验收必须覆盖：原枪放箱子、副本在玩家手里；两玩家分别持有；一个掉落一个背包；复制后立即射击（不等轮询）；表满时复制；读档刚完成时使用。给出扫描覆盖清单和已测试容器模组名称。

## 7. 维修、HUD 与电击枪

耐久寿命保持已确认值：手枪 1200、冲锋枪 2000、步枪 1500、霰弹枪 300、栓狙 200、半自动狙 500、机枪 4000、电击枪 100。每次实际射击/放电 1 点，创造 0；不引入卡壳或低耐久伤害削弱。损坏枪保留型号/弹量/消音器，可维修，不被原版磨损销毁。

维修报价冻结 record ID、Revision、当前/最大耐久、每项材料与库存引用。点击时重新核对，变化则刷新报价或取消，不用旧价格修新损伤。`Candidate.Durability` 动态 getter 不能代替报价快照。同型号同值枪交换也应通过实例/持有者和事务版本识别。按缺损比例向上取整；满耐久无需修、不扣料；按现有材料满修约新枪 20–30% 的目标核实当前配方，不顺手重平衡其他玩法。

HUD/详情读取提交后的只读快照；低于等于 20% 橙色，损坏明确文字，0<durability<1% 显示 `<1%`，99%<durability<100% 显示 `>99%`。实例值未改变时也要刷新，不以 item value 相同跳过状态更新。

电击枪：记录充能就绪的世界游戏时间，游戏关闭期间默认不额外充电；使用同一世界的游戏时钟，不用 wall clock。转移、切枪、放箱子、死亡掉落不重置/共享计时；读取时可惰性计算是否就绪，只有需要写入时通过事务确认。两把电击枪分别计时。损坏枪即使电已充好也不能放电；维修不重置/加速充能，也不无故恢复弹量。保存绝对游戏时间需验证同版本时钟继续性，若引擎不保证则保存剩余量并在加载时恢复；只采用经验证的一种方式。

## 8. 保存、布局和缺记录

正常玩法验收使用新世界；新增授权的迁移用未改写的 0.28.2 世界副本验证。显式布局/schema 必须优先，只有确定支持的组合才加载记录；未知非零戳不因存在表而放行。0.35.4 分类修复需走真实 Save/Load 验证，不能只测 Classify 常量。

被拒用的旧/未知世界不改写枪数据、不生成新记录。未知原始戳及记录子树应保留，不统一降格写成 4 后丢失来源信息。没有戳不等于必然新世界：结合已确认的历史键/版本标识判别；无法可靠判别时提示并停用，不猜物品位模式。无需为历史世界补枪或恢复型号。

枪表、Next 水位、schema 和所有持有者数据必须来自同一个游戏线程的一致快照；后台序列化使用快照，不遍历正在修改的记录。确认引擎 SaveProject 的完成语义，保存失败保持内存有效状态并给出失败结果；不把保存请求已发出当写盘成功。无记录 ID、型号与记录不匹配、损坏字段都不可用，不修补为满枪。

复制冲突清理和后台保存不能制造“物品已保存新 ID、记录未保存”或相反的跨快照状态。新增持有者扫描不等于获得 ID 回收授权。

## 9. 开箱与其他模组联动

检查当前 `ScCsgoBox` 是否真的发放枪械；若目前只有刀，明确记录“枪械发奖入口不存在/不适用”，不为验收新增枪械奖池。需要枪械发奖的既有入口统一使用名称/型号查询和新枪创建 API，不自行移位拼 data，不复制一把已用枪的 ID 作为奖励模板。

独立 repo 先核对各自 git/AGENTS，再改必要接口；不编辑对端未提交文件。枪模组未加载或 API 不匹配时拒绝该奖励且不吞箱子/钥匙；不支持的外部容器记录为未覆盖。验证普通枪通过 Stash、原版箱子后状态一致。枪状态引入的集成问题在 M4 内，`GunpowderKegBlock` 奖励名称等非耐久杂项继续暂停。

## 10. 实施顺序与检查点

只做同一个 M4 专项，按可审查提交拆分，不自动升级到 M5，也不因本方案自行指定发布日期。

| 顺序 | 交付内容 | 进入下一步前的证据 |
|---|---|---|
| D0 | 记录现有调用方/持有者清单；基于最新提交复现容量满换弹、复制共享、充能共享 | 小型失败复现与预期值，标明已修/仍失败 |
| D1 | 只读快照、记录修订号、显式事务返回、ID 分配失败机制 | 表满、缺记录、型号不符不扣料；已有记录正常操作 |
| D2 | 接入开火、换弹、消音器、维修；电击枪按实例充能 | 各入口故障注入、重复提交、精确扣量与报价变化 |
| D3 | 复制边界、持有者审计、必要开箱接口、保存一致性 | 复制即用、跨持有者、读档、失败保存与重复 ID 用例 |
| D4 | 全枪/设备回归与交付 | VPS 离线报告 + Windows/手机 M4 实机证据；其余批次仍 BLOCKED |

建议主要文件：`ScGunRegistry.cs`、`GunSpec.cs`、`SubsystemScGunBlockBehavior.cs`、`ScReloadTransaction.cs`、`ScInventoryTransaction.cs`、`ScWeaponRepair.cs`、`SubsystemScWeaponWorkbench.cs`、`ScAmmoHud.cs`、`ScGunBlock.cs`；必要新增 `ScGunTransaction`/持有者适配服务。现有渲染入口只改状态读取，不扩展绘制功能。

## 11. 必须通过的回归矩阵
