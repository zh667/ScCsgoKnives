## NEO 数组同步只在自己的适配层处理

旧问题是在 NMM 把人物换成 CT/T 大骨架后，NEO 仍可能使用原来较短的 ComponentRigidBody.AbsoluteBoneTransforms。NEO 钩子向数组写层级矩阵时越界。

新增 CsNeoBoneBuffer：

- 只处理本 mod 的 ComponentCsPlayerAppearance 所适配的目标组件，不全局修改所有生物。
- 在自己的模型刷新路径同步，另注册优先级 -100 的 OnModelCalculateBones 前置钩子，确保 NEO 的实际钩子执行前容量足够。
- 按当前模型骨骼、骨骼索引与网格数量确定容量；仅在不足时扩容，保留已有元素，同模型重复调用不重新分配。不缩短大缓冲，避免 CT/T/默认模型反复选择时抖动。
- 通过 NEO 的具名属性设置运行时缓冲；它在官方 1.4 中是 internal setter。没有替换 NEO 方法、操作混淆字段、修改程序集或添加全局 DLL 别名。
- 不跳过 NEO 钩子，不接管它的刚体逻辑；修复数组后仍运行原始第三方层级计算。

新测试使用真实 Neo 1.4：先给旧数组 1 个元素，调用原钩子确认重现 IndexOutOfRangeException，再执行我们的前置适配并重跑同一原钩子，检查全骨骼矩阵一致。覆盖默认→T→CT→默认→CT，以及真实钩子注册顺序。此前只测姿态数组的缺口已补上。

## 按需贴图准备，质量与原生参数不变

新 ScTexturePreparation 把 CPU 图片解码与 GPU 上传分开：

1. 小队装备确定、人物首次持有/更换武器时，请求实际需要的材质；不遍历预载整个枪皮目录。
2. 主线程复制原始资源字节、读取图片头部尺寸。ContentManager 共享流始终保持打开。
3. 后台使用与原生 ImageReader 相同的 Engine.Media.Image.Load 解码，不缩放、不改格式、不调质量、不重新压缩。
4. 解码结果在主线程发布到原生图片缓存，再让 ContentManager 的原生 Texture2DReader 上传纹理。GPU/Texture2D 创建仍在主线程，缓存和资源生命周期沿用引擎。

后台同时最多 2 个解码任务，最多 8 个未消费请求，预留解码像素预算 64 MiB；不满足预算或格式条件时走原生加载路径，**不降低全量图片尺寸**。预算指准备任务的估计 RGBA 像素开销，不是整个进程总内存上限。

ASTC/ASTC-sRGB 覆盖、已有原生缓存和原生后缀选择顺序保持兼容。重复请求去重；本轮不会创建额外常驻贴图副本。退出世界取消未发布任务并回收其结果，旧世界的结果不会发布到新世界。已交给 ContentManager 的图片/纹理不由准备队列擅自销毁。

如果渲染先于解码完成，仍需等待该资源；GPU 上传仍可能产生尖峰。因此本轮是候选性能改善，不宣称所有首用长帧已经消除。

## 重进世界装备准备

OnProjectLoaded 在原生实体和组件加载完成后枚举已恢复战术人物的实际装备，以小批量前瞻请求贴图/几何，并在加载阶段完成需要的纹理和 NPC GPU 缓冲准备。不重新随机装备，不修改实体、物品或存档字段。

仅处理这些人物装备涉及的资源，避免首个游戏渲染帧集中重建。重复准备命中原有缓存；退出世界后 GPU 缓冲仍正常释放，下一次重进重新准备。代价是部分工作转移到世界加载阶段，加载时间可能增加，不能当作这些工作完全消失。

背景几何解析沿用上一版有界任务；GPU 缓冲创建通过原来的网格对象缓存，共享与普通绘制相同的顶点、索引、贴图和 shader。三/五人小队的原子生成、物品消耗和失败回滚保持。

- CS_PERF summary：增加 texturePending/Started/Ready/WaitMs/UploadMs/Skipped。
- long-frame：使用双份帧计数，在新帧 AI 已开始时仍保留上一帧绘制作用域；输出实际 scopesFrame。回归专门验证上一帧 WeaponDraw 不会被新帧 EnemyAI 覆盖。

计时仍为包含子调用的 CPU 墙钟时间，不是 GPU 定时器；不同作用域不能无条件相加。冷资源日志继续限流，未增加逐帧大字符串输出。
