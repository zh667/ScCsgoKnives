## 2. 根因与症状分类

### R1：共享仓储的持有者身份识别错误（物流及 Sushi 真实 DLL 已复现并修复）

后续已确认另一条具体错误：`Sushi.ComponentSushiPersonBox` 转发到 `ComponentMiner.Inventory`，而旧适配使用 `GetField` 读取引擎的 **属性**，导致适配始终失败。现已直接读取实际引擎属性，玩家与六个代理认作一个底层库存；恢复归属也统一到玩家。见 [根因报告](sushi-person-box-root-cause-2026-09-12.md)。原日志匿名 holder 编号仍不能直接还原为每个现场对象。

物流多个 `ComponentStorageUnit` 可经同一 `VaultGuid` 访问同一 `StorageVault`。槽位读取、增删均转发到底层仓库，多个入口并不代表多份物品。

本模组 `ScGunHolders.Key` 以容器对象身份加槽位编号生成键，扫描器则枚举每个实现 `IInventory` 的组件。不同代理入口被当成独立持有者。

由代码可推导的问题链：

> 同一底层枪械被多个入口报告 → 误判复制 → 拆分并写回新编号 → 所有入口同时读到新编号 → 下一轮再次误判 → 不断消耗编号。

`ScGunMutation.Commit` 在 `NeedsClone` 时调用 `ScGunGrowth.StripGrowth`，所以成功误拆分还可能清除真实枪械的击杀与成长。尚未获得现场前后状态，不能宣称已确认玩家损失了多少击杀。

日志模式高度吻合，但 holder:403～409 只有运行时匿名编号，尚不能断言这七个对象一定属于同一个物流仓库。

定位：`src/ScCsgoKnives/World/ScGunHolders.cs` 的 `Key/Scan`、`SubsystemScGunBlockBehavior.cs` 的 `Holders/SplitDuplicates`、`ScGunMutation.cs` 的 `Commit`。

### R2：有限且不回收的编号空间（设计限制确认）

物品布局 v5 使用 10 位实例编号：0、1023 为新枪模板；1～1022 为状态记录。注册表的 `Next` 单调增加，无自动回收；事务失败后的弃置记录也保留编号水位。

- “1022 把”不等于世界当前真实持枪数量，还可能包含误拆分历史、销毁后遗留记录、隔离记录。
- 正常开枪、换弹、消耗耐久更新同一条记录，不会每次新建记录。
- R1 会放大本限制。单纯扩大容量不能根治持续误分配。
- 当前未扫描到引用，不等于可以删除；未加载容器、其他世界、特殊仓储和待归还物品均须考虑。

定位：`Rendering/GunSpec.cs` 的 v5 编码与 `World/ScGunRegistry.cs` 的 `PeekNextId/Publish/Abandon/Load`。

### R3：重复全量扫描、失败重试与日志刷屏（代码及日志确认）

`SubsystemScGunBlockBehavior.Update` 每 0.5 秒执行持有者扫描。每次非新枪事务的 `HolderLocator` 再次完整扫描，拆分失败仍逐项记录警告，缺少对不变失败状态的退避。

大型工业库存和共享代理会放大遍历、集合分配、事务准备及日志写入成本。它是明确的额外开销路径，但当前日志没有帧耗时，不能量化其占比或断言其解释全部卡顿。

### R4：状态满提示过度承诺（确认）

“已有的枪不受影响”不适用于仍需复制分离的已有枪。日志中的 `gun operation refused ... DuplicateUnresolved` 证明至少一次操作因状态保护被拒绝，不是单纯按键或动画问题。日志未注明动作类型，不单凭此行认定每次拒绝都是换弹。

### R5：问号枪（现象确认，缺失来源未定）

`ScGunBlock.GetDisplayName` / `GunSpec.TryGetSnapshot` 无法取得有效、型号匹配的记录时显示异常。可能涉及缺记录、隔离校验失败、型号不匹配或世界/库存记录不同步。

状态表满本身不会自动删除已有记录。现有日志缺加载过程，提供的世界不含故障数据；不得直接判为升级损坏、物流删记录或跨世界故障。显示改进不能代替恢复原状态。

### R6：渲染性能（成本路径确认，瓶颈待测）

`Cs2SkinnedMesh.Skin` 对手臂等逐顶点 CPU 蒙皮；`CsmcFirstPersonRenderer` 与 `KnifePbrRenderer` 存在部件绘制、动态几何提交及 PBR/法线材质成本。不能把所有枪体说成逐顶点 CPU 蒙皮，枪械刚性部件有独立路径。

聊天中的 CPU 增幅不是受控帧耗时测量。需分开测量逻辑扫描、CPU 蒙皮、绘制提交、GPU 与内存；压缩包体积不等同于运行性能。

### 不属于根因：物品整数很长

截图 `1071645020` 在截图对应的物品编码下解出型号 0（AK-47）、实例 1022；其十进制位数不代表记录条数或计算复杂度。跨存档必须先读取方块映射，禁止把 348 写死为 CS 枪械。

## 3. 实施顺序与边界

### P0：先建立复现与无损对照

- 仅用新测试世界或完整副本，记录模组哈希、引擎/API 版本、原始物品值、状态表水位与枪械字段。
- 两个或七个相连物流仓储单元形成共享仓库，放入已实例化枪械（普通与计数器分别测；不要求必须有计数器）。
- 先验证“同一底层槽位经多个入口被报告”，再观察旧代码是否持续发布新编号。扫描自动运行，不依赖反复打开界面或退出重进。
- 有剩余编号时预期可能看到成功拆分及水位增长；只有耗尽后才应出现 `DuplicateUnresolved`。不能把后者当成唯一复现判据，也不必手造 1022 把枪。
- 精确满表边界可用隔离自动测试夹具构造，不向玩家正式世界批量灌入记录。
- 问号枪暂无已验证复现步骤；反复搬运、存读档只是排查矩阵，不保证产生该问题。

### P1：修复底层库存身份

- 提供统一持有者解析入口，返回真实底层存储身份及映射后的槽位，而非仅代理对象身份。
- 对物流已确认的 `VaultGuid/StorageVault` 实现可验证的适配；没有安装物流时不得引入强制依赖或加载失败。
- 普通箱子保持独立；相同型号、编号或相同内容不代表同一底层槽位，不能按物品值简单去重。
- 支持后续代理库存适配扩展；不能宣称可自动识别任意模组的所有共享库存。
- 扫描去重、事务重复判断、库存修订/锁定及恢复归属一起审查，避免只改显示键。处理共享仓库合并、拆分和槽位整理后的映射变化。
- 对同一枪在共享入口间访问、存取和涂装，不重分配编号，不清除成长；真实复制仍按原规则隔离。

### P2：控制扫描、重试及诊断成本

- 在保证跨模组库存变更可被识别的前提下，消除一次审计中的重复全量枚举，设置处理预算。
- 评估快照/索引与失效机制；外部模组未通知的变化仍需兜底，不能仅用陈旧缓存批准事务。
- 对满表及不变冲突退避；失败原因或底层持有关系改变后再及时处理，不能永久屏蔽真实复制。
- 日志按冲突身份、原因及状态变化去重，保留首次与汇总。诊断时记录容器类型、底层仓库身份、槽位、水位及耗时，不持续输出无关隐私。
- 不把关闭日志当成解决重复事务；正常发布仅保留必要提示和错误。

### P3：提示和缺记录诊断

- 满表提示改成“编号空间已耗尽，需新编号的操作暂不可用；无需新编号的独立已有枪仍可使用”等准确表述，不宣称所有旧枪正常。
- 区分满表、复制冲突、缺记录、型号不匹配及格式不支持。
- 布局与型号可靠时可保留名称/图标，明确“状态待恢复”；禁止猜测弹药、耐久或等级放行。

### P4：已满表存档的恢复专项（待现场与独立批准）

先止住误分配，再处理历史结果。修复识别不会自动恢复剩余编号，也不会自动恢复已经丢失的等级。

1. 获取故障完整世界、加载日志和问题前备份，核对每个世界的方块映射、注册表、库存及归还队列。
2. 只读生成引用与候选历史链报告，区分真实重复、共享入口别名、缺失、隔离与暂未发现引用。
3. 历史记录字段相同或相似不单独构成“同一把枪”的身份凭据；不能自动选最高等级覆盖当前枪。
4. 提出可核验的恢复方案及无法恢复项，经批准后在完整备份的副本执行，保留恢复清单并验证两轮存读档。
5. 编号回收、容量扩展或物品布局升级另行设计与审批，不属于本规划文档写入动作；禁止截断位、复用已有 ID、只改 Next 或清表。

### P5：独立性能验收

同设备、同世界、同位置与画质，对比：不持枪/持枪、普通箱/共享仓库、无冲突/有冲突；记录扫描频次和 p50/p95 耗时、事务重扫次数、帧时间尖峰、内存与日志速率。修复逻辑开销后再判断是否需要模型 LOD、纹理或动画优化，不修改玩法数值来掩盖卡顿。

## 5. 新增反馈：动画、输入、属性页和手柄

2026-09-12 追加。以下八项独立于共享仓库满表，不能混为同一根因。来源包括用户反馈、正式源码与视频 `D:/下载/༺༂黎༒雾༂༻_2026-09-12 11.57.29_QQ20260912-115633-HD.mp4`（约 9.71 秒，主要展示刀具切换）。离线抽帧不代表完成实机复现。

### U1：滚轮切走刀具，旧刀短暂重新播放切刀

- 已定位时序矛盾：原版 `ComponentFirstPersonModel` 在切换过渡中仍绘制旧 `m_value`；`KnifeAnimationController.Update` 却用当前新 `ActiveSlotIndex` 与旧绘制物品一起调用 `ScHeldWeaponSelection.Observe`，旧刀可能被误认作新装备并触发 deploy。
- 目标：明确区分选中物品与正在绘制物品。切出旧刀不能重播入场；切入新刀正常播放一次。不能仅删除刀具 deploy 动画。
- 验收：刀→空手、刀→原版物品、刀→枪、刀→刀、快速往返滚轮，以及菜单内换槽；同时检查动画和切刀音效。

### U2：开火按钮存在时，屏幕空白区域仍开火

- 代码确认：`SubsystemScGunBlockBehavior.UpdateGun` 将原版 `Dig/Hit` 与自定义开火 OR 合并，按钮没有替代触屏攻击。
- 增加“触屏开火方式”：仅开火按钮／保留触屏攻击。仅按钮模式下空白区域负责视角，不触发枪械开火。
- 仅按钮模式必须保证有效开火按钮可见可用；关闭按钮或总开关时提示并阻止无输入死路，或明确回退，具体交互在实施前确定。
- 根据输入来源过滤触摸攻击，不笼统清空已合并的全部 `PlayerInput`；保留鼠标、键盘映射、手柄和非枪物品原有交互。
- 验收覆盖 Android 多指、滑动视角、切换输入设备、按钮隐藏、暂停及后台恢复。

### U3：属性返回后配方串页、空白；配件显示“可持续发射器”

- 串页冲突已从两侧代码定位：装配台、属性页、装配页会覆盖 `ScreensManager.m_screens["RecipaediaRecipes"]`，没有恢复原入口。
- 玩家 `RecipaediaEX-2.0.0.1` 在该入口注册自己的页面，调用时传入 `IRecipaediaItem`；CS 页面预期整数物品值。覆盖后可能错误回退默认枪械或空白装配页。
- 目标：CS 属性页与装配页使用独立注册名，明确页面入口、返回所有者和参数契约；兼容原版 `GetBlockRecipeScreen` 与 RecipaediaEX 的子页面识别。避免用全局入口替换和任意弹出历史栈维持导航。
- 不把“不认识的参数”静默转成 AK 属性；应由入口适配解析或明确拒绝。
- “配件全变成可持续发射器”尚未定因：`ScWeaponMaterialBlock.GetDisplayName` 固定返回材料名，未发现属性页直接改名。需区分配方标题/列表显示错误与真实物品类型变化。
- 仍需：同次复现的完整日志、背包悬停截图、配方截图，确认是否为之前的模组组合。不能宣称修导航必然解决物品名异常。
- 验收：装配台→属性→返回→任意原版/其他模组配方，连续重复；属性↔装配配方、帮助↔描述、退出重进；检查其他材料实际值及名称保持不变，原版与 RecipaediaEX 分别测试。

### U4：枪械换弹未结束切刀，刀具入场动画丢失

- 明确风险点：离开枪械路径 `CancelReload(player,state)` 调用不校验动作归属的 `KnifeAnimationController.CancelAction`，直接设为 idle。若新刀已启动 deploy，旧枪取消可能误取消新刀动作；具体调度顺序需复现。
- 枪→枪已有 `cancelAnimation:false`，不能据此认为枪→刀已覆盖。
- 目标：取消绑定旧武器、旧动作/动作序号；处理真实换弹事务，但不取消新武器动作。不通过强制完成换弹或补弹规避。
- 验收：换弹开始、退匣、插匣、结束前各时点切刀；弹药与旧换弹取消规则保持，刀具 deploy 仅一次。必要时补具体枪型与视频。

### U5：准星参数自定义
